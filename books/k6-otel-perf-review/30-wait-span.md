---
title: "待っている時間を計装する"
---

修正前のバージョンに毎秒100件をかけたとき、`catalog-api`は1件あたり約2,519msを、`inventory`を呼ぶ前に使っていました。この時間の候補は、`inventory`を呼ぶ前の5msの処理と、同時実行数の制限の前で空きを待つ時間の2つです。5msの処理が2.5秒に伸びたとは考えにくいので、待ち時間だろうと見当はつきます。ただ、見当がつくことと1件ずつ確かめられることは違います。

## 足すスパンの区間を先に決める

スパンを足す前に、測りたい区間を一文で書き出してみましょう。いま確かめたいのは「`catalog-api`が`inventory`を呼ぶための空きを待っている時間」です。この一文から、スパンの始まりと終わりが決まります。始まりは空きを要求した時点で、終わりは空きを得た時点です。

順序を逆にして、内部の関数に片端からスパンを付けてから眺めても、スパンの数が増えるだけで問いには答えられません。待ち時間を表すスパンが1つあればよい場面で、5msの処理や応答の組み立てにまでスパンを付けると、[Tempo](https://grafana.com/docs/tempo/v3.1.x/)のトレースの画面で確かめたい区間が見つけにくくなります。

## 待機区間のスパン

`catalog-api`でセマフォの空きを待つ処理は、`acquire`という関数です。この関数の中で、空きを待つ区間だけを表すスパンを作りました。待っている件数と待った時間は、メトリクスとしても記録しています。

```go
acquire := func(ctx context.Context) error {
	start := time.Now()
	waiting.Add(ctx, 1)
	defer waiting.Add(ctx, -1)
	ctx, span := tracer.Start(ctx, "wait for backend slot", trace.WithSpanKind(trace.SpanKindInternal))
	defer span.End()
	select {
	case slots <- struct{}{}:
		waitHist.Record(ctx, time.Since(start).Seconds())
		return nil
	case <-ctx.Done():
		span.SetStatus(codes.Error, "canceled while waiting")
		return ctx.Err()
	}
}
```

`select`は、セマフォの枠が空くのと、コンテキストが取り消されるのを同時に待ちます[^kind]。待っている間に利用者が接続を切るとコンテキストが取り消されるので、そのときはスパンにエラーの状態を付けます。

[^kind]: サンプルのコードでは、この計装を環境変数`INSTRUMENT_WAIT`で入れたり外したりできるようにしており、抜粋は入れたときの処理です。スパンの種別には`INTERNAL`を使います。リモートの呼び出しではなく、アプリケーションの中の処理を表すからです。スパンの種別は[Tracing API（v1.61.0）](https://github.com/open-telemetry/opentelemetry-specification/blob/v1.61.0/specification/trace/api.md#spankind)で定義されています。`INTERNAL`はデフォルト値で、"Indicates that the span represents an internal operation within an application" と説明されています。

メトリクスとスパンは同じ待ち時間を別の粒度で表します。`catalog.limiter.wait.duration`のヒストグラムと、待っている件数を表す増減するカウンターの`catalog.limiter.waiting`が示すのは、ある時間範囲で何件がどれだけ待ったかの集計です。スパンは、どのリクエストがどれだけ待ったかを1件ずつ示します。メトリクスは「いま待ちが増えているか」をダッシュボードやアラートで見るために使い、スパンは個々の遅いリクエストの内訳を確かめるために使います。

## 足す前と足した後

まず、負荷が軽く待ちがはっきり出る条件で比べました。負荷は修正前のバージョンに閉じたモデルの10VUで30秒ずつかけ、変えたのはスパンの有無だけです。Tempoから300件のトレースを取り出して区間ごとの時間を集計しました。エラーになったリクエストはないので、どの行も同じ300件です。

| 区間 | スパンなし 中央値 | p(95) | スパンあり 中央値 | p(95) |
| --- | --- | --- | --- | --- |
| `catalog-api`のサーバースパン | 127.4ms | 153.2ms | 128.5ms | 147.6ms |
| `catalog-api`のクライアントスパン | 51.3ms | 60.9ms | 51.0ms | 60.6ms |
| サーバーとクライアントの差 | 75.8ms | 97.7ms | 78.3ms | 94.5ms |
| 空きを待つスパン | なし | なし | 72.8ms | 88.6ms |

スパンがないときも、サーバーとクライアントの差から、`catalog-api`の中で約76msを使っていることは分かりました。分からなかったのは、その76msの中身です。スパンを足すと、1件ごとに約73msが空きを待つ時間、残りの約5.5msがapi内の処理と分かれます。

6章の条件、つまり修正前のバージョンに毎秒100件をかけたテストでも、スパンを足して流し直しました。Tempoのトレースを1件、Grafanaで開いてみましょう。

![catalog-apiのサーバースパン2.57秒の下に、wait for backend slotのスパン2.53秒がほぼ全体を占め、その後ろにHTTP GETの42ms、inventoryのGET /stock/{id}とlookup stockが続く](/images/20261118-grafana-trace-wait-span.png)
*図2: 修正前のバージョンに毎秒100件をかけたテストのトレースを1件、GrafanaのExploreで表示した画面*

6章で`inventory`を呼ぶ前の時間とした約2.5秒は、ほぼすべてが空きを待つスパンに入りました。300件の中央値では、サーバースパンの2,567.6msのうち、空きを待つスパンが2,510.3ms、`inventory`を呼んでいたクライアントスパンが52.1msで、api内の処理は約5msです。

スパンを足しても、[k6](https://grafana.com/docs/k6/v2.3.x/)から見た結果はほとんど変わりませんでした。10VUのテストで、完了の頻度は毎秒77.0件と77.3件、p(95)は150.4msと150.0msです。計装そのものの負荷は、10章で別に測ります。

## 確かめられるようになった仮説

スパンを足す前に確かめられたのは、「`catalog-api`の中で`inventory`を呼ぶ前に時間を使っている」という仮説までです。スパンを足した後は、「その時間の大半は同時実行数の制限の前で空きを待つ時間である」という仮説をリクエストごとに確かめられます。開発担当が上限を4から16に上げたときの見立ては、ここで観測に裏付けられました。

ただし、この裏付けは修正前のバージョンについてのものです。上限を上げれば、`catalog-api`での待ちは減るでしょう。その代わりに、`inventory`へ届く同時の要求が増えます。2章で決めた`inventory`の処理枠は6件で、待ち行列は8件です。`inventory`の側の待ちには、まだスパンがありません。6章では、`inventory`のサーバースパンと`lookup stock`の差から処理枠の空きを待つ時間を推し量りました。修正前の`catalog-api`で、サーバーとクライアントの差から待ちを推し量ったのと同じ方法です。
