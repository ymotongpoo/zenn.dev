---
title: "待っている時間を計装する"
---

修正前の版に毎秒100件をかけたとき、`catalog-api`は1件あたり約2,519msを、`inventory`を呼ぶ前に使っていました。この時間の候補は2つあります。`inventory`を呼ぶ前の5msの処理と、同時実行数の制限の前で空きを待つ時間です。5msの処理が2.5秒に伸びたとは考えにくいので、待ち時間だろうと見当はつきます。ただ、見当がつくことと1件ずつ確かめられることは違います。

## 足すスパンを先に言葉で決める

スパンを足す前に、どの区間を測りたいのかを言葉で決めます。いま確かめたいのは「`catalog-api`が`inventory`を呼ぶための空きを待っている時間」です。この一文が決まれば、スパンの始まりと終わりも決まります。始まりは空きを要求した時点で、終わりは空きを得た時点です。

順序が逆になると、つまり内部の関数に片端からスパンを付けてから眺めると、スパンの数は増えても問いには答えられません。待ち時間を表すスパンが1つあればよい場面で、5msの処理や応答の組み立てにまでスパンを付けると、トレースの画面でも[Tempo](https://grafana.com/docs/tempo/v3.1.x/)の容量でも、確かめたい区間が埋もれます。

## 待機区間のスパン

`catalog-api`でセマフォの空きを待つ処理は、`acquire`という関数です。この関数の中で空きを待つ間だけ、スパンを開くようにしました。待っている件数と待った時間は、メトリクスとしても記録しています。

```go
acquire := func(ctx context.Context) error {
	start := time.Now()
	waiting.Add(ctx, 1)
	defer waiting.Add(ctx, -1)
	ctx, span := tracer.Start(ctx, "wait for backend slot", trace.WithSpanKind(trace.SpanKindInternal))
	defer span.End()
	select {
	case slots <- struct{}{}:
		waitHist.Record(ctx, time.Since(start).Seconds())
		return nil
	case <-ctx.Done():
		span.SetStatus(codes.Error, "canceled while waiting")
		return ctx.Err()
	}
}
```

題材のコードでは、この計装を環境変数`INSTRUMENT_WAIT`で入れたり外したりできるようにしています。抜粋は入れたときの処理です。スパンの種別には`INTERNAL`を使います。リモートの呼び出しではなく、アプリケーションの中の処理を表すからです[^kind]。待っている間に利用者が接続を切るとコンテキストが取り消されるので、そのときはスパンにエラーの状態を付けます。

[^kind]: スパンの種別は[Tracing API（v1.61.0）](https://github.com/open-telemetry/opentelemetry-specification/blob/v1.61.0/specification/trace/api.md#spankind)で定義されています。`INTERNAL`はデフォルト値で、"Indicates that the span represents an internal operation within an application" と説明されています。

メトリクスとスパンは同じ待ち時間を別の粒度で表します。`catalog.limiter.wait.duration`のヒストグラムと、現在待っている件数を表す増減するカウンター（UpDownCounter）の`catalog.limiter.waiting`が示すのは、ある時間範囲で何件がどれだけ待ったかの集計です。スパンは、どのリクエストがどれだけ待ったかを1件ずつ示します。前者は「いま待ちが増えているか」をダッシュボードやアラートで見るために使い、後者は個々の遅いリクエストの内訳を確かめるために使います。

## 足す前と足した後

まず、負荷が軽く待ちがはっきり出る条件で比べました。負荷は修正前の版に閉じたモデルの10VUで30秒ずつかけ、変えたのはスパンの有無だけです。Tempoから300件のトレースを取り出して区間ごとの時間を集計しました。エラーになったリクエストはないので、どの行も同じ300件です。

| 区間 | スパンなし 中央値 | p(95) | スパンあり 中央値 | p(95) |
| --- | --- | --- | --- | --- |
| `catalog-api`のサーバースパン | 127.3ms | 151.2ms | 131.2ms | 151.5ms |
| `catalog-api`のクライアントスパン | 50.8ms | 61.5ms | 52.3ms | 61.3ms |
| サーバーとクライアントの差 | 77.0ms | 96.4ms | 78.3ms | 97.5ms |
| 空きを待つスパン | なし | なし | 72.8ms | 91.9ms |

スパンがないときも、サーバーとクライアントの差から、`catalog-api`の中で約77msを使っていることは分かりました。分からなかったのは、その77msの中身です。スパンを足すと、1件ごとに約73msが空きを待つ時間、残りの約5.5msがapi内の処理と分かれます。

6章の条件、つまり修正前の版に毎秒100件をかけた試験でも、スパンを足して流し直しました。

| 区間 | 中央値 | p(95) |
| --- | --- | --- |
| `catalog-api`のサーバースパン | 2,586.2ms | 2,627.8ms |
| 空きを待つスパン | 2,532.9ms | 2,567.6ms |
| `catalog-api`のクライアントスパン | 51.2ms | 61.2ms |

6章で`inventory`を呼ぶ前の時間とした約2.5秒は、ほぼすべてが空きを待つスパンに入りました。2.6秒のうち、`inventory`を呼んでいたのは約51ms、api内の処理は約6msです。

スパンを足しても、[k6](https://grafana.com/docs/k6/v2.3.x/)から見た結果はほとんど変わりませんでした。10VUの試験で、完了の頻度は毎秒77.2件と76.6件、p(95)は151.3msと152.6msです。計装そのものの負荷は、10章で別に測ります。

## 確かめられるようになった仮説

スパンを足す前に確かめられたのは、「`catalog-api`の中で`inventory`を呼ぶ前に時間を使っている」という仮説までです。スパンを足した後は、「その時間の大半は同時実行数の制限の前で空きを待つ時間である」という仮説をリクエストごとに確かめられます。開発担当が上限を4から16に上げたときの見立ては、ここで観測に裏付けられました。

ただし、この裏付けは修正前の版についてのものです。上限を上げれば、`catalog-api`での待ちは減るでしょう。その代わりに、`inventory`へ届く同時の要求が増えます。2章で決めた`inventory`の処理枠は6件で、待ち行列は8件です。`inventory`の側の待ちには、まだスパンがありません。6章では、`inventory`のサーバースパンと`lookup stock`の差から、処理枠の空きを待つ時間を推し量りました。修正前の`catalog-api`でサーバーとクライアントの差から待ちを推し量ったのと、同じ方法です。
