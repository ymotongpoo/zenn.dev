## 同じアプリケーションで比べる

コードを変えずに済むなら、OBIのほうが手軽に見えます。5章から9章では、同じ `report` を2つの方法で動かしました。CPANのSDKで計装する方法と、OBIで外から観測する方法です。どちらの方法でも、HTTPのリクエストを受ける区間と `rates` を呼ぶ区間はトレースになり、Goのサービスまでつながりました。違いが出たのは、それ以外の部分です。

| 比較の軸 | CPANのSDK | OBI |
| --- | --- | --- |
| アプリケーションの変更 | PSGIのファイルに4か所。PSGIサーバーでは送信の回避策も必要（8章） | 不要。OBIのコンテナを追加する |
| 実行環境の条件 | Perl 5.30以降（API、SDK、エクスポーターの要件） | Linux 5.8以降とBTF、特権またはeBPFの権限、ホストのPID名前空間。影響を受けるカーネルではtracefsとcgroupのマウント（9章） |
| サーバーのスパン | 名前は `GET request`。`http.route` と `server.port` が無い | 名前は `GET /report`。`http.route`、`server.port` などがある |
| プロセスの中の区間 | `in_span` で業務処理ごとに作れる。属性も付けられる | 作れない。処理中の時間は `processing` の1区間 |
| `rates` への伝搬 | 計装が `traceparent` を書く | カーネルの側で `traceparent` を書き込む |
| preforkのサーバー | Simpleプロセッサーなら全件届く | 全件正しく対応づく |
| イベントループのサーバー | 検証していない | 並行するリクエストの親子を誤って対応づける |
| 応答時間への影響 | Simpleプロセッサーで、デフォルトのBatchより5ms余り（直列）、未計装より14ms余り（Starman、8並列）増えた | 未計装との差は数ミリ秒以内 |
| サービス名 | `OTEL_SERVICE_NAME` の値 | `perl` になった。`OTEL_SERVICE_NAME` は使われなかった |
| ログ | SDK 0.029-TRIALで送れる。トレースIDが付く | 検証していない |

表のうち「検証していない」の2つは、本書の実験の範囲外です。OBIのドキュメントには、ログとトレースを関連づける機能やHTTPのメトリクスを作る機能の説明もあります。ただし、本書で確かめたのはOBIのトレースだけです。

## OBIが向く場面

OBIが向くのは、まずサービスの間のつながりと区間の長さを知りたい場合です。前提は、Linuxで動くPerlのアプリケーションがpreforkか単一プロセスのサーバーを使っていることです。コードに手を入れずに、どのサービスのどのリクエストが遅いのかまでは分かります。アプリケーションの依存も増えません。応答時間への影響も、本書の測定ではほとんど現れませんでした。

その代わりに、9章で見た3つの条件を満たす必要があります。OBIのコンテナに特権を与えられること、カーネルの不具合に応じたマウントを用意できること、サービス名を別の方法で付けられることです。ドキュメントの `discovery.instrument` の説明には、計装対象ごとに名前を上書きできるとあります。本書ではこの方法を試していません。

## SDKが向く場面

SDKが向くのは、プロセスの中の区間を見たい場合です。9章のOBIのトレースからは、`days=180` のリクエストの540ms余りがPerlの中で使われたことまでしか分かりませんでした。5章のSDKのトレースなら、それが集計処理の `aggregate` で、日数が180だったことまで分かります。業務の文脈を属性として持たせられるのは、プロセスの中で計装する方法だけです。

eBPFを使えない環境でも、SDKなら動きます。コンテナに特権を与えられない実行基盤や、Linux以外の開発機がそうです。ログをトレースと関連づけたい場合も、いまはSDKの試験版を使うことになります。

8章で見たとおり、SDKの弱点は送信の仕組みがPSGIサーバーの実行方式と噛み合っていないことです。Simpleプロセッサーを使えば届きますが、応答時間が延び、延びた分はサーバーのスパンの長さにも含まれます。Batchプロセッサーなら、IO::Asyncのループを進めるミドルウェアと終了時の `force_flush` を自分で書くことになります。

## 両方を同時に使う構成

同じアプリケーションで、プロセスの中の区間をSDKで、通信の区間をOBIで取る構成も考えられます。ただ、両方がHTTPのサーバーとクライアントのスパンを作るので、そのままでは同じ区間が二重に記録されます。OBIの対策は、自分でトレースやメトリクスを送っているプロセスを検出したら、そのプロセスの計装を止めることです。この振る舞いは設定 `exclude_otel_instrumented_services` で決まり、デフォルトで有効です[^exclude]。本書ではこの構成を試していないので、PerlのプロセスでOBIが計装を止めるかどうかも確かめていません。

[^exclude]: OBIのドキュメントの[Exclude OTel instrumented services](https://opentelemetry.io/docs/zero-code/obi/configure/service-discovery/#exclude-otel-instrumented-services)にあります。

TwiggyやMojoliciousのようなイベントループのサーバーには、どちらの方法でもまだ確かな答えを出せていません。OBIは親子を誤って対応づけ、SDKではコンテキストの引き継ぎを検証していません。Perlのイベントループで動くアプリケーションをトレースするには、どちらかの側に作業が必要です。
