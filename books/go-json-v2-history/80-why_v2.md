## v2を作るときの3原則

標準ライブラリにv2を置く考え方は、Russ Cox が2024年5月に書いた["Evolving the Go Standard Library with math/rand/v2"](https://go.dev/blog/randv2)にまとまっています。3つの原則が挙げられています。

1つ目は、インポートパスの規約です。セマンティックインポートバージョニングによって `math/rand` と `math/rand/v2` は別のパッケージとして扱われ、同じプログラムの中に共存できます。これが技術的な前提です。新しいパッケージを足しても、誰も勝手にimportしません。

2つ目は、利用者への敬意です。変更は十分に動機づけられ、移行のコストに見合うものでなければなりません。既存のパッケージが出発点であり、本当の問題を直すのであって、好みで作り替えるのではありません。

3つ目が、v1利用者の支援です。理想的には、v2がv1の薄いラッパーになる（あるいはその逆になる）ことで、v1を使い続ける人も修正や性能改善を受け取れます。Russ Cox は、これが常に達成できるとは限らない、とも書いています。

`encoding/json/v2` は、この3つ目を反転した強い形で満たしました。v1がv2のラッパーになったからです。

これによって、v1を使い続ける人も速いunmarshalの実装を使うことになります。`encoding/json` のバグ修正は、これからv2の側に入ります。2つの実装を並行して保守する必要もありません。2020年10月のREADMEにあった「v1の実装は永久に残さなければならない。であれば、v1をv2の上で実装できると都合がよい」は、保守の都合の話でしたが、結果としては互換性の問題の解消にもなりました。

同じブログには、こういう記述もあります。

> There will not be a glut of v2 packages in the next few Go releases. Instead, we will handle one package at a time…
> Many packages will not need a v2 at all.
>
> （今後数回のGoリリースでv2パッケージが大量に出ることはありません。かわりに、一度に一つのパッケージを扱っていきます。多くのパッケージにv2はまったく必要ありません。）

実際 `math/rand/v2` がGo 1.22、`encoding/json/v2` がGo 1.27、と5リリース分の間隔があります。

## おわりに

2016年3月10日に「パーサーがメンバー名の大文字小文字を無視する」という issue が立ち、2026年5月13日に `encoding/json/v2` の提案が受理されました。10年2ヶ月です。`encoding/json` がGo 1.0に入ってからなら14年です。

この期間を停滞と呼ぶことはできます。危険なデフォルト値だと分かっていて、[修正パッチ](https://go-review.googlesource.com/c/go/+/224079)まで書かれていて、それでも動かなかったのですから。

一方で、この期間に起きたことを並べると、別の見え方もします。修正を試して測って断念する。別の名前で作り直す構想を書く。プロトタイプを作り、本番サービスで3年動かす。議論を開き、96件のコメントを受けて設計を練り直す。提案を出し、229名の議論を sub-issue に分けて処理する。実験フラグの下で1年間、実際の利用者に使ってもらう。そしてデフォルトを反転させ、古い実装を退避経路として残したまま切り替える。どの段階も飛ばされていません。そして最終的に、既存のコードは1行も変えなくてよい形に着地しました。

最終形としての現状が面白いのは、互換性が二者択一でなくなったことです。`DefaultOptionsV1()` を置いてから個別のオプションで上書きすれば、v1とv2のあいだの好きな地点を指定できます。「壊さない」と「直す」のどちらかを選ぶ問題だったものが、どこまで寄せるかを呼び出しごとに決める問題になりました。

同時に、すべてがきれいに片付いたわけでもありません。`format` タグはリリース直前に取り下げられ、`time.Duration` は標準ライブラリの中でシリアライズする手段を失ったまま出ました。その機能に触るには、標準に取り込まれたはずの外部モジュールを使うことになります。言語側の未確定な提案が、標準ライブラリの機能を1つ削る形で作用しました。これらは[リリースノート](https://go.dev/doc/go1.27)に書かれていません。

自分のライブラリを保守していると、同じような問題に出会います。この挙動は誤りだと分かっているけれど、直せば、それに依存している何かが壊れる。そのとき取れる選択肢は、我慢するか壊すかの2つではありません。別の名前で作り、古いほうを新しいほうの上に載せ直す、という道があります。コストは高いですし、実際に `encoding/json` の場合、構想から正式化まで6年かかりました。

冒頭の1行に戻ります。

```go
json.Unmarshal([]byte(`{"NAME":"gopher"}`), &u)
```

Go 1.27でも、このコードは `encoding/json` では `Name` に `gopher` を入れます。14年前とまったく同じです。そして `encoding/json/v2` に書き換えた瞬間から、入らなくなります。どちらの挙動が要るのかを、呼び出しごとに決められるようになりました。14年かけて手に入ったのは、厳密なJSONライブラリそのものよりも、この選べるという状態のほうだと思います。

課題も残っています。型付き構造体タグの提案は保留のままで、`format` タグが標準に戻るのかは決まっていません。`GOEXPERIMENT=nojsonv2` というオプションも、いずれ消えます。そのとき、2010年に書かれたあの `encode.go` はツリーから削除されます。14年分の判断に名前を付けたフラグの一覧だけが、あとに残ります。

`encoding/json/v2` はリリースされましたが、これからも関連する機能の動向を追うのが楽しみです。
