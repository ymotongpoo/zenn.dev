---
title: "OSとカーネル"
---

前章の絵には、プログラムが1つしか出てきませんでした。実際のコンピュータでは、多数のプログラムが同じCPUと同じ物理メモリの上で同時に動いています。それでも互いのメモリを踏み荒らさずに済んでいるのは、OS（オペレーティングシステム）がプログラムごとに「独り占めしているような見せかけ」を作っているからです。

その見せかけの中身にあたるプロセスと仮想メモリ、OSの中核である**カーネル**との境界、そしてカーネルが管理する実行の単位であるスレッドを順に見ます。eBPFはカーネルの中で動く仕組みなので、この章の言葉がそのまま7章で必要になります。

## 実行ファイルとプロセス

ディスクの上にある実行ファイルと、それを起動して動いている実体は別物です。動いている実体のほうを**プロセス**と呼びます。1つの実行ファイルから、プロセスは何個でも起動できます。

OSは各プロセスに**PID**（プロセスID）という番号を振って区別します。GoからはPIDを `os.Getpid()` で見られます。

* [Go Playgroundで実行する](https://go.dev/play/p/IeLA_nGTgDW)

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	x := 42
	fmt.Printf("PID: %d  xのアドレス: %p\n", os.Getpid(), &x)
}
```

同じバイナリを2回実行すると、こうなります。

```
PID: 25  xのアドレス: 0x179411378070
PID: 31  xのアドレス: 0x13456066e070
```

同じプログラムの同じ変数なのに、PIDも、変数のアドレスも実行ごとに違います。この違いは手元で2回動かすと確かめられます。Playgroundは1つの隔離された環境の中で動くため、何度実行してもPIDは同じ値のままです。このアドレスの違いが、次の節の主題です。

![実行ファイルとプロセス](/images/20260820-program-vs-process.png)
*図1: 矢印は起動の関係を表す。1つの実行ファイルから起動された2つのプロセスは、別々のPIDと別々のメモリを持ち、互いに独立して動く。*

## 仮想メモリ

プロセスから見えているアドレスは、物理メモリの棚の番号そのものではありません。プロセスごとに用意された、専用の番地の列です。これを**仮想アドレス**と呼び、仮想アドレスが物理メモリのどこに対応するかは、カーネルが対応表で管理します。

この仕組みの結果、あるプロセスのアドレス `0x179411378070` と、別のプロセスの同じアドレスは、無関係の場所を指します。プロセスは自分の仮想アドレス空間の外に触れないので、隣のプロセスのメモリをアドレス指定で読むことはできません。前節の実験で2つの実行のアドレスが違ったのも、それぞれが自分専用の空間を持っているからです。

![仮想アドレスと物理メモリ](/images/20260820-virtual-to-physical.png)
*図2: 矢印は対応を表す。2つのプロセスはそれぞれ自分専用の仮想アドレス空間を見ており、カーネルの対応表を介して物理メモリの別々の場所に割り当てられる。*

:::message
アドレスが実行ごとに変わるのには、もうひとつ理由があります。**ASLR**（アドレス空間配置のランダム化）というセキュリティ機構が、スタックやヒープの開始位置を起動のたびにずらしているのです。攻撃者に「あの変数は必ずこの番地にある」と狙わせないための仕組みで、本書の実験でアドレスの値が毎回変わるのは主にこのためです。
:::

## アドレス空間の区分

プロセスの仮想アドレス空間は、用途ごとの領域に分かれます。機械語が置かれる**テキスト領域**、グローバル変数の**データ領域**、そして**ヒープ**と**スタック**です。

ヒープとスタックの違いは、寿命と管理者です。スタックは関数を呼ぶと伸び、抜けると縮みます。片付けを気にしなくていい代わりに、関数を抜けたあとまで値を残せません。ヒープは明示的に確保する領域で、関数を抜けても残ります。その代わり、誰かが解放するか、Goのように回収する仕組みが要ります。Goではどちらに置くかをコンパイラが判断し、ローカル変数のアドレスを返す関数を書けば、その変数はヒープに移ります。

![プロセスに与えられるメモリ](/images/20260820-process-memory.png)
*図3: 上下はアドレスの高低を表し、スタックは高いほうから低いほうへ、ヒープは低いほうから高いほうへ向かって伸びる。*

2章で見たレジスタと合わせると、実行中のプロセスの全体像が描けます。`SP` はこの図のスタックの先端を指し、`PC` はテキスト領域の中の、いま実行している命令を指しています。

![プロセスのメモリとCPU](/images/20260820-memory-and-cpu.png)
*図4: 矢印は、レジスタがメモリ上のどこを指しているかを表す。右の表はこの節で見たメモリの区分である。*

## ユーザー空間とカーネル空間

CPUには実行の特権レベルがあり、アプリケーションのコードは制限された側で動きます。この側を**ユーザー空間**、制限のない側を**カーネル空間**と呼びます。ユーザー空間のプログラムは、ディスクやネットワークカードに直接命令を出せません。

なぜ制限するのでしょうか。仮想メモリの対応表を管理し、プロセスを互いに隔離しているのはカーネルです。もしどのプログラムでもハードウェアや対応表を直接操作できたら、この隔離はただのお願いになってしまいます。制限のない側をカーネルだけに絞ることで、見せかけが守られています。

![ユーザー空間とカーネル空間](/images/20260820-user-kernel-space.png)
*図5: 矢印はお願いの向きを表す。実線はアプリからカーネルへの依頼、破線は結果が返ること、赤い破線はできないことを示す。*

## システムコール

ハードウェアに触りたいときは、カーネルに頼みます。この頼み方が**システムコール**です。ファイルを読む `read`、書く `write`、通信の口を開く `socket` などが用意されていて、Goの `os.ReadFile` も内側ではシステムコールを呼んでいます。頼まれたカーネルがハードウェアを操作し、結果を返します。

見た目は関数呼び出しですが、通常のGoの関数呼び出しとは中身が違います。普通の呼び出しは同じ特権レベルのまま次の命令へジャンプするだけです。システムコールでは専用の命令でカーネル側へ切り替わり、カーネルが処理を終えてから戻ってきます。切り替えの分だけ、普通の関数呼び出しより高くつきます。

本当にカーネルへ渡っているのかは、外から眺められます。Linuxには、プログラムが発行するシステムコールを表示する `strace` というコマンドがあります。ファイルを1つ読んで印字するだけのプログラムで試します。

[Go Playgroundで実行する](https://go.dev/play/p/ntDv_zJWS4p)

```go
package main

import (
	"fmt"
	"os"
)

func main() {
	data, err := os.ReadFile("/etc/hostname")
	if err != nil {
		panic(err)
	}
	fmt.Print(string(data))
}
```

これをビルドして `strace` にかけます。Goのランタイムが起動時に読むファイルまで全部出てくるので、`openat`、`read`、`write` の3つに絞り、末尾だけを抜き出しました。

```
$ strace -e trace=openat,read,write ./readfile
...
openat(AT_FDCWD, "/etc/hostname", O_RDONLY|O_CLOEXEC) = 4   ← ファイルを開く
read(4, "mymachine\n", 512)             = 10                ← 中身を読む
read(4, "", 502)                        = 0                 ← 終端に達した
write(1, "mymachine\n", 10)             = 10                ← 画面へ書く
+++ exited with 0 +++
```

Goのソースに書いたのは `os.ReadFile` と `fmt.Print` の2つだけです。その内側で、開く、読む、書くという3種類のシステムコールがカーネルへ渡っています。`= 4` はカーネルが返した番号で、以降の `read` はこの番号でファイルを指しています。

eBPFは、このカーネル側で動くプログラムです。ユーザーが書いたコードをカーネルの中に置くのですから、そのままでは危険です。何が危険で、どう防いでいるのかは、7章で見ます。

## スレッド

1つのプロセスの中で、複数の処理の流れを並行して動かせます。この流れひとつひとつが**スレッド**です。

同じプロセスのスレッドたちは、仮想アドレス空間を共有します。ヒープに置いた値はどのスレッドからも見えます。一方でスタックだけは、スレッドごとに専用の領域を1本ずつ持ちます。関数呼び出しの積み降ろしは流れごとに独立だからです。

どのスレッドをいつCPUに載せるかを決めるのはカーネルで、この割り当てを**スケジューリング**と呼びます。カーネルが作り、番号を振り、スケジュールする実行の単位はスレッドまでです。この「までです」が後で問題になります。6章で見るように、Goはこの上に独自の実行単位（goroutine）を重ねていて、それはカーネルからは見えません。

![プロセスとスレッド](/images/20260820-process-threads.png)
*図6: この図に矢印はない。1つのプロセスの中に複数のスレッドがあり、各スレッドは自分のスタックを持ち、ヒープとテキスト領域は共有される。*

## この章で各難所に関係する知識

- プロセスは自分専用の仮想アドレス空間を持ち、外から他プロセスのメモリをアドレス指定では読めない。だから「外から観測する」には特別な仕組みが要る。
- スタックは関数呼び出しとともに伸縮する領域で、ヒープは関数を抜けても残る。
- スタックはスレッドごと専用で1本ずつあり、ヒープは複数のスレッドで共有される。
- カーネルが知っている実行の単位はスレッドまでで、その先はカーネルからは見えない。

## 確認問題

1. ローカル変数のポインタを返す関数を書いたとき、その変数がスタックに置かれたままだと何が起きるでしょうか。Goのコンパイラはこれをどう解決しているでしょうか。
2. `os.ReadFile` が「ただの関数呼び出し」で済まず、システムコールを必要とするのはなぜでしょうか。この章の言葉で説明してください。

:::details 解答
1. スタックのその領域は関数を抜けた時点で回収され、次の関数呼び出しで別の値に上書きされます。返したポインタは無効な場所を指すことになります。Goのコンパイラはこれを検出して、その変数をヒープに置きます（エスケープ解析）。
2. ディスクの読み取りはハードウェアの操作であり、ユーザー空間のプログラムには許されていないからです。制限のないカーネル空間に切り替わって、カーネルに代行してもらう必要があります。その頼み方がシステムコールです。
:::
