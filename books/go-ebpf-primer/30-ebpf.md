## カーネルの中で動く小さなプログラム

[eBPF](https://ebpf.io/)は、ユーザーが書いた小さなプログラムをLinuxカーネルの中にロードして、特定のイベントが起きたときに実行させる仕組みです。イベントとは、システムコールが呼ばれた、パケットが届いた、ある命令アドレスに到達した、といったものを指します。カーネルを再ビルドしたり、カーネルモジュールを書いたりする必要はありません。仕様と実装はLinuxカーネルの一部で、[カーネル側のドキュメント](https://docs.kernel.org/bpf/)にまとまっています。

たとえば「`openat` システムコールが呼ばれたら、そのファイル名を記録する」「ある命令アドレスに到達したら、その時刻を控える」といった処理を書けます。本書で扱うのは後者、つまりユーザー空間のプログラムの特定のアドレスにフックを置く使い方です。

3章で見たとおり、カーネル空間は制限のない側です。そこで任意のコードを走らせるのですから、そのままでは危険です。

## 検証器が課す制約

危険を防いでいるのは**検証器**（verifier）です。ロード時にプログラム全体を静的に解析し、通らなければロード自体が失敗します。検証器が保証するのは、プログラムが必ず停止すること、未初期化のメモリやポインタを読まないこと、許可されたメモリ以外に触らないことです。振る舞いはコンパイラの型検査に近いものです。Goのコンパイラが型の合わない代入をコンパイルエラーにするように、検証器は安全性を証明できないプログラムをロードエラーにします。走らせてから落ちるのではなく、載せる前に断られるわけです。

この検証を成立させるために、eBPFプログラムにはいくつもの制約が課されます。命令数に上限があり、ループは検証器が終わりを確かめられる形でしか書けません。回数を定数で決め打ちするのが基本で、実行時に回数を渡せる `bpf_loop` のような専用のヘルパーもありますが、いずれにしても上限のない繰り返しは書けません。「リストを終端まで辿る」ような、素直でありながら停止性を証明しにくいコードは通りません。この制約は難所4で具体的な形をとって現れます。

## イベントをまたいで状態を持つマップ

カーネル側で動くeBPFプログラムは、イベントごとに呼ばれてすぐ終わります。関数のローカル変数に相当するものは、次のイベントには残りません。イベントをまたいで状態を持つには、**マップ**（map）と呼ばれるカーネル管理のキーバリューストアを使います。役割はGoの `map` と似ています。違うのは、実体がカーネル側にあり、eBPFプログラムからもユーザー空間のプロセスからも読み書きできる点です。

「関数の入口で開始時刻を記録し、出口でそれを取り出して所要時間を計算する」という計装の基本パターンは、このマップの上で成り立っています。難所4で登場する `ongoing_goroutines` も、goroutineの親子関係を保持するマップです。

![マップで入口と出口をつなぐ](/images/20260911-map-pattern.png)

## uprobeとuretprobe

eBPFでユーザー空間のプログラムにフックを仕掛ける主な仕組みは2つあります。

- **uprobe**：ユーザー空間バイナリの「特定の命令アドレス」に置くプローブ。関数の先頭アドレスに置くことが多いため「入口のフック」と呼ばれがちだが、仕組み上は入口専用ではなく、バイナリ中の任意の命令アドレスに置ける。
- **uretprobe**：関数から「戻るタイミング」を捕捉するための特別な仕組み。

uprobeを「置く」というのは、バイナリの中身を実際に書き換える操作です。カーネルは、指定された命令アドレスにある命令を控えておき、その先頭の1バイトをブレークポイント命令に差し替えます。amd64ではこの命令は `int3`、機械語では `cc` の1バイトです。4章で逆アセンブルした `double` の先頭に置くなら、`48 01 c0`（`ADDQ AX, AX`）の `48` が `cc` に変わり、残りのバイトはそのまま残ります。ただし、この機械語が載っているのは、4章で見たとおり読み取り専用の共有ページです。カーネルは共有ページを直接書き換えるのではなく、コピーオンライトでそのプロセス専用のコピーを作り、コピーの側の1バイトを差し替えて、対応表の指す先を切り替えます。ディスク上の実行ファイルも、共有していた元のページも変わりません。

CPUがそのアドレスまで進むと、差し替えられた1バイトを実行してトラップし、カーネルに入ります。ここで疑問が1つ残ります。`cc` はどのuprobeでも同じ1バイトで、踏まれた `cc` 自体には「どのuprobeか」という情報がありません。カーネルが見るのは、トラップした瞬間のPCの値です。その値を、uprobeの登録の表（どのファイルの先頭から何バイト目に置いたか）と突き合わせて、踏まれたのがどのuprobeかを特定します。表に載っていなければ、デバッガなど別の誰かが置いたブレークポイントとして扱われます。

こうして特定されたuprobeに結び付けられたeBPFプログラムが走ります。このときカーネルは、トラップした瞬間のレジスタ一式を保存してあり、eBPFプログラムはそのコピーを受け取ります。レジスタの中身は普通、他のプロセスから見ることはできませんが、渡されたコピーなら読めます。これが難所2に関係します。走り終えると、カーネルは控えておいた元の命令を別に用意した領域で実行し、続きの命令へ処理を戻します。対象のプログラムから見れば、命令が1つ実行されただけです。レジスタもスタックも、元のまま返ってきます。

uretprobeは、これに一手間を足したものです。まず関数の入口にuprobeを置きます。発火するのは関数の先頭の命令に着いた瞬間で、5章で見たとおり、そこでは `SP` が戻りアドレス（`CALL` が積んだあの数値）のスロットを指しています。カーネルはそのスロットの値を退避しておき、同じ場所に、自分で用意したトランポリンのアドレスを書き込みます。対象の関数を逆アセンブルする必要も、フレームの大きさを調べる必要もありません。関数が末尾の `RET` を実行すると、呼び出し元ではなくトランポリンへ飛び、そこでまたトラップします。カーネルは戻り側のeBPFプログラムを走らせてから、退避しておいた本物の戻りアドレスへジャンプします[^uretprobe-arch]。

[^uretprobe-arch]: 戻りアドレスがスタックにあるのはamd64の話です。arm64では、関数の入口の時点で戻りアドレスがまだリンクレジスタ（`x30`）にあるため、カーネルが書き換えるのはそのレジスタです。関数のプロローグがその値をスタックへ退避するので、以降の話は同じになります。

2つの違いは、書き換える相手です。uprobeが書き換えるのは機械語の1バイト、つまりコードの領域にある値だけです。uretprobeはそれに加えて、スタックの上にある値を書き換えます。この差が、難所1の分かれ目になります[^uretprobe-syscall]。

[^uretprobe-syscall]: Linux 6.11以降のamd64には、トランポリンでトラップする代わりに専用のシステムコールを呼ぶ最適化が入りました。切り替えの費用は下がりましたが、戻りアドレスを書き換える点は変わりません。

相手が変われば、書き換え方も変わります。コードの領域は読み取り専用の共有ページなので、さきほど見たとおりコピーオンライトの回り道が要ります。スタックは、そのプロセスが自分で読み書きしながら使っている領域です。保護を外す手間はなく、コピーも差し替えも起きません。3章で「外から他プロセスのメモリをアドレス指定では読めない」と書いたのはユーザー空間どうしの話で、カーネルはその制限を受けない側にいます。対象プロセスのページをそのまま書き換えるので、書き込まれた値は、そのプログラムが次にそのスロットを読んだ時点から使われます。

![uprobeとuretprobeの挿し込み](/images/20260911-probe-insertion.png)
*図3: 矢印は処理の順序を表す。uprobeは命令の先頭1バイトを差し替えてトラップさせ、元の命令は別に用意された領域で実行される。uretprobeは入口のuprobeで、スタック上の戻りアドレスをトランポリンのアドレスに書き換える。*

一般的な計装では、関数の入口にuprobe、出口にuretprobeを置き、「入口で開始時刻を記録、出口で所要時間を計算」というパターンを取ります。多くの言語ではこれで素直に動きます。Goでは、この素直な形が最初の一歩から使えません。

## Goで書かれたローダー

eBPFプログラム自体は制限されたCで書き、専用のコンパイラでバイトコードに落とします。しかし、そのバイトコードをカーネルにロードし、プローブを実際のアドレスに結びつけ、マップを読み出す側は、普通のユーザー空間のプログラムです。そしてこのローダー側は、多くの場合Goで書かれています。デファクトのライブラリが [`github.com/cilium/ebpf`](https://github.com/cilium/ebpf) で、OBIもこれを使っています。

uprobeを1つ仕掛けるコードを見ておきます。

```go
// コンパイル済みeBPFプログラム objs は事前にロード済みとする
exe, err := link.OpenExecutable("/proc/12345/exe")
if err != nil {
	return err
}

// シンボル名を指定して関数の先頭に置く
up, err := exe.Uprobe("main.handleRequest", objs.OnEntry, nil)
if err != nil {
	return err
}
defer up.Close()
```

第1引数にシンボル名を渡すと、そのシンボルの先頭アドレスにプローブが置かれます。シンボル名の代わりに、アドレスを直接指定する形もあります。

```go
up, err := exe.Uprobe("", objs.OnReturn, &link.UprobeOptions{
	Address: 0x9e290, // 命令のファイル内オフセット
})
```

シンボル名を空文字列にして `Address` を渡すこの形が、難所1の回避策そのものになります。渡す値には注意が要ります。uprobeはそもそも「ファイルの先頭から何バイト目か」で登録する仕組みなので、ここに書くのも仮想アドレスではなくファイル内のオフセットです。シンボル名を渡した場合はライブラリが変換してくれますが、`Address` を直に渡すときは自分で `readelf -lW` の `p_vaddr` と `p_offset` を見て、`オフセット = 命令の仮想アドレス - p_vaddr + p_offset` を計算します。逆アセンブルに出る `0x49e290` をそのまま渡すと、意図した命令には置かれません。OBIがこの変換をどこで行っているかは12章で見ます。なお、ここに挙げた2つのコードは動かすのにroot権限とLinuxが要るので、読むだけでかまいません。手元で実行して確かめるのは、これ以降に出てくるGoのサンプルのほうです。
