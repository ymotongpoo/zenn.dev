前章までで、実行ファイルの中身と、それがプロセスとしてメモリに載るところまでを見ました。ここからは、実行中にいちばん頻繁に起きること、つまり関数呼び出しの仕組みを見ます。難所1の戻りアドレスも難所2の引数の受け渡しも、どちらもここから直接出てきます。

## スタックフレーム

関数を呼ぶと、スタックにその関数の作業領域が積まれます。これを**スタックフレーム**と呼びます。フレームにはローカル変数や、あとで使う値を退避したものが置かれ、関数を抜けると捨てられます。3章で見たとおりスタックは高い番地から低い番地へ伸びるので、呼び出しが深くなるほど、新しいフレームは低い番地に積まれます。

ここで、関数の「置き場所」を2つに区別しておきます。関数の命令そのものは4章で見た `.text` にあり、何度呼ばれても動きません。スタックに積まれるのは、その関数の1回の呼び出しぶんの実行状態のほうです。この後の実験では同じ関数が4回呼ばれますが、命令は1か所のまま、フレームだけが4つ積まれます。

これは2章で見たポインタで観察できます。再帰で呼び出しを深くしながら、各深さのローカル変数のアドレスを印字します。`//go:noinline` の意味はこの章の最後で説明します。

* [Go Playgroundで実行する](https://go.dev/play/p/hQeDJJuwQ2Q)

```go
package main

import (
	"fmt"
	"unsafe"
)

//go:noinline
func descend(depth int) {
	var local [64]byte
	addr := uintptr(unsafe.Pointer(&local[0]))
	fmt.Printf("深さ%d: localのアドレス = %#x\n", depth, addr)
	if depth < 3 {
		descend(depth + 1)
	}
}

func main() {
	descend(0)
}
```

```
深さ0: localのアドレス = 0x17ef0a08eeb8
深さ1: localのアドレス = 0x17ef0a08ee08
深さ2: localのアドレス = 0x17ef0a08ed58
深さ3: localのアドレス = 0x17ef0a08eca8
```

深さが1つ増えるごとに、アドレスがちょうど176バイトずつ下がっています。1回の呼び出しで積まれる `descend` のフレームの大きさが176バイトだ、ということです。関数を抜けるときには、この積まれた分がそのまま捨てられます。

![関数呼び出しとスタックフレーム](/images/20260820-stack-frame.png)
*図1: この図に矢印はない。上下はアドレスの高低で、`descend` の呼び出しが深くなるたびに、フレームが176バイトずつ低い番地へ積まれていく。*

## CALLとRET

フレームに積まれるものはもう1つあります。**戻りアドレス**です。amd64では `CALL` 命令が、呼び出しの次の命令のアドレスをスタックに積んでからジャンプします。関数末尾の `RET` 命令は、積まれたその値を取り出してそこへジャンプします。つまり「どこへ戻るか」は、スタック上の1つのスロットに書かれたただの数値です。

4章の `double` の例で、呼び出す側を逆アセンブルすると実物が見えます。

```
$ go tool objdump -s 'main\.main$' demo
  ...
  main.go:11   0x49e1b3   e8c8ffffff     CALL main.double(SB)   ← ここで呼ぶ
  main.go:11   0x49e1b8   440f117c2428   MOVUPS X15, 0x28(SP)   ← 戻ってきたら次はここ
  ...
```

`CALL` 命令のアドレスは `0x49e1b3` で、その次の命令は `0x49e1b8` にあります。この `CALL` が実行される瞬間、スタックには `0x49e1b8` という数値が積まれます。`double` の末尾の `RET` は、スタックからこの数値を取り出して、そこへジャンプします。

呼ばれた側も見ておきます。4章で逆アセンブルした `double` の中身は、2命令しかありませんでした。

```
$ go tool objdump -s 'main\.double$' demo
  main.go:7   0x49e180   4801c0   ADDQ AX, AX
  main.go:7   0x49e183   c3       RET            ← スタックから 0x49e1b8 を取り出してジャンプする
```

`RET` の行を見ると、どこへ戻るのかがどこにも書かれていません。オペランドを持たない `c3` という1バイトの命令です。戻り先はスタックにあるので、命令のほうは「積まれている値へ戻れ」としか言っていません。

![CALLとRETによる戻りアドレスの受け渡し](/images/20260820-call-ret-timeline.png)
*図2: 矢印は時間の前後を表す。CALLが「次の命令のアドレス」をスタックに積み、呼ばれた関数のRETがそれを取り出してジャンプする。戻り先の情報は、スタック上の1スロットに書かれた数値がすべてである。*

この数値をカーネルが書き換えるのが、難所1で扱う `uretprobe` の仕組みです。書き換える相手がスタックの上にある、という点を覚えておいてください。

## 呼び出し規約

引数の置き場所は、フレームの中とはかぎりません。呼ぶ側がどこに値を置き、呼ばれた側がどこから読むか。この取り決めを**呼び出し規約**と呼びます。取り決めですから、両側が同じ規約に従ってさえいれば、置き場所はどこでも成立します。

代表的な方式は2つあります。引数をスタックに積んで渡す方式と、レジスタに入れて渡す方式です。スタック渡しは、フレームの決まった位置を見れば外からでも引数を読めます。レジスタ渡しはメモリを経由しないぶん速い代わりに、どの引数がどのレジスタに入るかという対応表を知らなければ読めません。

さきほどの出力に、その実例が写っています。`CALL main.double(SB)` の直前の行を見てください。

```
  main.go:11   0x49e1ae   b815000000   MOVL $0x15, AX   ← 引数21(=0x15)をAXに入れる
  main.go:11   0x49e1b3   e8c8ffffff   CALL main.double(SB)
```

`double(21)` の引数21が、スタックではなくレジスタ `AX` に入れられてから呼ばれています。そして4章で見た `double` の本体は `ADDQ AX, AX` でした。呼ぶ側が `AX` に置き、呼ばれた側が `AX` から読む。この対応こそが規約です。

プラットフォームには標準の呼び出し規約があり、Linuxのamd64ならCのプログラムはみなそれに従います。外から観測する道具も、当然その標準を前提に作られています。Goがこの標準に従っていないことが、難所2の主題になります。

![スタック渡しとレジスタ渡し](/images/20260820-convention-stack-vs-register.png)
*図3: 同じ `f(a, b, c)` の呼び出しでも、規約によって引数の置き場所が変わる。外から引数を読むには、どちらの規約か、どの位置かを知っている必要がある。*

## インライン展開

ここまでの話には、暗黙の前提がありました。関数の呼び出しが、機械語の上でも `CALL` として残っていることです。この前提は、常には成り立ちません。

コンパイラは、小さな関数の呼び出しを、関数の中身をその場に展開する形に置き換えることがあります。これを**インライン展開**と呼びます。`CALL` と `RET` のひと往復と引数の受け渡しが丸ごと消えるので、実行は速くなります。コンパイラの判定は `-gcflags=-m` で見られます。

```
$ go build -gcflags=-m main.go
./main.go:6:6: can inline double
./main.go:11:20: inlining call to double
```

`//go:noinline` は、この展開を禁止して呼び出しを `CALL` として残させる指示です。本書のサンプルコードが繰り返しこれを付けているのは、展開されてしまうと観察対象の呼び出しそのものが消えてしまうからです。通常のアプリケーションで書く必要はありません。

展開の影響は観察だけにとどまりません。外から関数の出入りを捕まえるには、その関数の命令アドレスを指定して観測点を置きます。展開されて呼び出しごと消えていれば、指定できる番地がありません。小さなアクセサやラッパーほど、計装からは見えなくなります。4章の確認問題で「書いたはずの関数がシンボルテーブルに無い」ことがあったのも、これが理由です。番地があった場合に観測点をどう置くのかも、4章の続きです。置く先は読み取り専用の共有ページに載った機械語なので、コピーオンライトでページごと差し替えることになります。実際の挿し込みは7章で見ます。

![インライン展開で消える計装点](/images/20260820-inlining.png)
*図4: 矢印は変換の向きを表す。インライン展開は呼び出しの命令そのものを消すので、フックを置くアドレスがなくなる。*

## この章で各難所に関係する知識

- 戻りアドレスは、CALLがスタックの1スロットに書き込むただの数値である。難所1のuretprobeは、これを書き換える。
- 引数の置き場所は呼び出し規約が決める。レジスタ渡しは速いが、外から読むには対応表が要る。難所2はこの対応表の話になる。
- インライン展開された関数には、フックを置くアドレスそのものが無い。

## 確認問題

1. `descend` の実験で、`local` の配列の大きさを `[64]byte` から `[128]byte` に変えると、印字されるアドレスの間隔はどう変わるでしょうか。予想してから確かめてください。
2. `double` から `//go:noinline` を外してビルドし、`go tool objdump -s 'main\.main$'` の出力から `CALL main.double` を探してください。見つからないのはなぜでしょうか。

:::details 解答
1. フレームにはローカル変数のほかに戻りアドレスなどの固定分も積まれるので、間隔は「64バイト増えて240になる」とは限りませんが、およそ64バイト広がります。手元の測定では176バイトから240バイトになりました。
2. `double` がインライン展開され、呼び出しが `CALL` として残っていないからです。`main.main` の中に `double` の中身（2倍の計算）が直接埋め込まれています。このときシンボル `main.double` 自体もバイナリから消えます。
:::
