前章でeBPFの仕組みを見ました。ここからは本書の題材である**OpenTelemetry eBPF Instrumentation**（OBI）を紹介します。生い立ち、全体の動き、使い方、そして計装の2つの経路です。難所の章はOBIの実装の細部に入っていくので、その前に全体の動きを押さえておきます。

## Beylaから始まった生い立ち

OBIは、もともとGrafanaが開発していたeBPFベースの自動計装ツール**Beyla**を前身とします。2025年5月にOpenTelemetryプロジェクトへの寄贈が発表され、同年10月30日に最初のリリース `v0.1.0`（alpha）が出ました。2026年3月のKubeCon EUでbetaに到達し、その後もおよそ月1回のペースでリリースが続いています。Beylaも消えたわけではなく、OBIを基盤とするGrafanaのディストリビューションとして続いています。開発の本流はOBI側にあり、Beylaのメンテナは現在OBIのリポジトリで作業しています。

本書が参照するのは2026年8月17日の `v0.11.0` で、執筆時点の最新は同年8月20日の `v0.12.1` です。リポジトリは [`open-telemetry/opentelemetry-ebpf-instrumentation`](https://github.com/open-telemetry/opentelemetry-ebpf-instrumentation) です。

## OBIは何をするものか

OBIは、それ自体が1つのプログラムです。観測したいアプリケーションと同じマシンかコンテナ環境で動かすと、対象のプロセスを見つけ、eBPFプログラムを仕込み、対象を変更せずにHTTPやgRPCのトレースとメトリクスを取り出して、OpenTelemetryのバックエンドへ送ります。アプリ側に必要な作業はありません。これが1章で述べたゼロコード計装の実体です。

起動からエクスポートまでは、次の段階を通ります。

1. **発見**: `/proc` を定期的に走査して、動いているプロセスとその開いているポートを列挙します。全プロセスを計装するわけではなく、利用者が設定で与えた条件（実行ファイルのパス、ポート番号、Kubernetesのメタデータなど）に合うものだけを対象に選びます。ポーリングの負荷を下げるために、新しいポートのbindをeBPFで検知する補助も入っています。
2. **ELF解析**: 対象の実行ファイルを解析して、言語と種別を判定します。Goバイナリなら、シンボルテーブルや `.gopclntab` から計装したい関数のアドレスを、DWARFやオフセット表から構造体フィールドの位置を割り出します。4章で見た「実行ファイルに残る情報」が、ここでまとめて使われます。
3. **ロードとアタッチ**: コンパイル済みのeBPFプログラムをカーネルにロードして検証器を通し、解析で得たアドレスへuprobeなどのフックを結び付けます。
4. **イベント収集**: フックが発火するたびに、eBPFプログラムがカーネル側でイベントを組み立て、リングバッファ（カーネルとユーザー空間で共有するイベントの受け渡し口）に書き込みます。OBIのユーザー空間側はそれを読み取り、リクエスト単位のスパンに組み立てます。
5. **エクスポート**: スパンにKubernetesやコンテナのメタデータを付け、OTLP（OpenTelemetryの標準プロトコル）でトレースバックエンドへ送ります。メトリクスはOTLPのほかPrometheus形式でも出せます。

## 使ってみる

OBIはLinux専用で、カーネル5.8以降（BTF有効）を必要とします。eBPFプログラムをロードする都合上、root権限か、それに相当するcapabilityの組が要ります。

いちばん手軽なのはDockerです。ポート8080で待ち受けるアプリを観測して、取れたスパンを画面に印字するだけなら、次のように動かせます。

```
docker run --rm \
  -e OTEL_EBPF_OPEN_PORT=8080 \
  -e OTEL_EBPF_TRACE_PRINTER=text \
  --pid=host --privileged \
  otel/ebpf-instrument:v0.11.0
```

`--pid=host` はホストのプロセスを見えるようにする指定、`--privileged` は特権の付与です。カーネルに手を入れる道具なので、この種の権限は避けて通れません。

主な設定は環境変数で渡します。よく使うものを挙げます。

| 環境変数 | 意味 |
|---|---|
| `OTEL_EBPF_OPEN_PORT` | このポートを開いているプロセスを対象にする |
| `OTEL_EBPF_AUTO_TARGET_EXE` | 実行ファイルのパス（グロブ）で対象を選ぶ |
| `OTEL_SERVICE_NAME` | スパンに付けるサービス名 |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | OTLPの送信先（OpenTelemetry標準の変数をそのまま使う） |
| `OTEL_EBPF_TRACE_PRINTER` | デバッグ用にスパンを標準出力へ印字する |
| `OTEL_EBPF_BPF_CONTEXT_PROPAGATION` | 難所4で扱うコンテキスト伝搬の有効化（既定は無効） |

Kubernetesでは、各ノードに1つずつ置くDaemonSetとして動かす形が代表的です。`hostPID: true` を付ければ、ノード上の全プロセスを1つのOBIが観測します。OpenTelemetry Collectorに組み込むためのreceiverも用意されています。

本書の主題は「動かし方」ではなく「なぜ動くのか」なので、セットアップの詳細は[公式ドキュメント](https://opentelemetry.io/docs/zero-code/obi/)に譲ります。

## 2つの計装経路

OBIの計装は、`SUPPORT_MATRIX.md` にあるとおり2つのカテゴリに分かれます。

一つは**ネットワークレベルのプロトコル計装**で、こちらは言語に依存しません。接続の確立や送受信といったカーネル内のソケット処理に、kprobeやソケットフィルタでフックを置き、流れるバイト列をHTTP/1.1、HTTP/2、gRPC、MySQL、PostgreSQL、Redis、Kafkaなどとして解釈します。アプリが何語で書かれていても、ソケットを通る限り観測できます。TLSで暗号化された通信も、OpenSSLの共有ライブラリの関数にuprobeを置いて、暗号化される前と復号された後の平文を捕まえます。

もう一つが**ランタイムやライブラリのレベルの計装**で、こちらは対象の環境ごとに個別の実装が要ります。そしてライブラリレベルの関数計装を持つのはGoだけです。`net/http` と `database/sql` はGo 1.17以降、`google.golang.org/grpc` は1.40以降、というようにサポート範囲がバージョン単位で決まっています。本書が扱う4つの難所は、すべてこの後者の経路で起きるものです。

![OBIの2つの計装経路](/images/20260820-obi-two-paths.png)
*図2: 矢印は分類の枝分かれを表す。プロトコル計装は言語に依存しない。関数レベルまで踏み込む計装はランタイムとライブラリごとの実装が要り、それを持つのはGoだけである。*

プロトコル計装だけでも所要時間やステータスコードは取れます。それでもGoに対して関数レベルまで踏み込むのは、ソケットに現れない情報があるからです。たとえばリクエストを処理しているgoroutineの系譜（難所4）はソケットからは見えませんし、直列化前の構造体から値を読めれば、プロトコルの解釈に頼らず正確な値が取れます。

## リポジトリの構成

難所の章では、OBIのソースコードを繰り返し引用します。どこに何があるのか、主要な区画を挙げておきます。

| 場所 | 役割 |
|---|---|
| `bpf/` | カーネル側で動くeBPFプログラムのCソース |
| `bpf/gotracer/` | Goバイナリの関数計装（本書の主役） |
| `bpf/generictracer/` | 言語非依存のプロトコル計装 |
| `bpf/tpinjector/` | コンテキスト伝搬のヘッダ注入（難所4の第2経路） |
| `pkg/` | ユーザー空間側のGoコード |
| `pkg/internal/goexec/` | GoバイナリのELF解析とオフセット解決（難所1と3の主役） |
| `pkg/ebpf/` | eBPFプログラムのロードとアタッチ、リングバッファの読み取り |
| `pkg/export/` | OTLPとPrometheusへのエクスポート |
| `cmd/obi/` | 本体バイナリのエントリポイント |

要するに、カーネル側（C）が `bpf/`、ユーザー空間側（Go）が `pkg/` です。難所の章で引用するファイルは、ほぼすべて `bpf/gotracer/` と `pkg/internal/goexec/` と `pkg/ebpf/` のどれかに入っています。

## この章から難所へ持っていくもの

- OBIは「発見→ELF解析→ロードとアタッチ→イベント収集→エクスポート」というパイプラインで動く独立したプログラムである。
- 計装経路は2つあり、言語非依存のプロトコル計装と、Goだけが持つ関数レベルの計装に分かれる。4つの難所はすべて後者で起きる。
- カーネル側のCコードは `bpf/`、ユーザー空間側のGoコードは `pkg/` にある。
