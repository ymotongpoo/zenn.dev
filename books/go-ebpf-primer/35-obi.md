前章でeBPFの仕組みを見ました。ここからは本書の題材である**OpenTelemetry eBPF Instrumentation**（OBI）を紹介します。生い立ち、全体の動き、そして計装の2つの経路です。難所の章はOBIの実装の細部に入っていくので、その前に全体の動きを押さえておきます。

## Beylaから始まった生い立ち

OBIは、もともとGrafanaが開発していたeBPFベースの自動計装ツール**Beyla**を前身とします。2025年5月にOpenTelemetryプロジェクトへの寄贈が発表され、同年10月30日に最初のリリース `v0.1.0` が出ました。その後もおよそ月1回のペースでリリースが続いています。上流での位置づけは開発中（Development）で、`VERSIONING.md` は利用者に見える部分がまだ安定していないこと、`v0` のマイナーバージョン間で互換性のない変更が入りうることを明記しています。Beylaも消えたわけではなく、OBIを基盤とするGrafanaのディストリビューションとして続いています。開発の本流はOBI側にあり、Beylaのメンテナは現在OBIのリポジトリで作業しています。

本書が参照するのは2026年9月4日の `v0.13.0` です。リポジトリは [`open-telemetry/opentelemetry-ebpf-instrumentation`](https://github.com/open-telemetry/opentelemetry-ebpf-instrumentation) です。

## OBIは何をするものか

OBIは、それ自体が1つのプログラムです。観測したいアプリケーションと同じマシンかコンテナ環境で動かすと、対象のプロセスを見つけ、eBPFプログラムを仕込み、対象を変更せずにHTTPやgRPCのトレースとメトリクスを取り出して、OpenTelemetryのバックエンドへ送ります。アプリ側に必要な作業はありません。これが1章で述べたゼロコード計装の実体です。

起動からエクスポートまでは、次の段階を通ります。

1. **発見**: `/proc` を定期的に走査して、動いているプロセスとその開いているポートを列挙します。全プロセスを計装するわけではなく、利用者が設定で与えた条件（実行ファイルのパス、ポート番号、Kubernetesのメタデータなど）に合うものだけを対象に選びます。ポーリングの負荷を下げるために、新しいポートのbindをeBPFで検知する補助も入っています。
2. **ELF解析**: 対象の実行ファイルを解析して、言語と種別を判定します。Goバイナリなら、シンボルテーブルや `.gopclntab` から計装したい関数のアドレスを、DWARFやオフセット表から構造体フィールドの位置を割り出します。4章で見た「実行ファイルに残る情報」が、ここでまとめて使われます。
3. **ロードとアタッチ**: コンパイル済みのeBPFプログラムをカーネルにロードして検証器を通し、解析で得たアドレスへuprobeなどのフックを結び付けます。
4. **イベント収集**: フックが発火するたびに、eBPFプログラムがカーネル側でイベントを組み立て、リングバッファ（カーネルとユーザー空間で共有するイベントの受け渡し口）に書き込みます。OBIのユーザー空間側はそれを読み取り、リクエスト単位のスパンに組み立てます。
5. **エクスポート**: スパンにKubernetesやコンテナのメタデータを付け、OTLP（OpenTelemetryの標準プロトコル）でトレースバックエンドへ送ります。メトリクスはOTLPのほかPrometheus形式でも出せます。

## どこで動かすか

OBIはLinux専用で、カーネル5.8以降（BTF有効）と、eBPFプログラムをロードできる権限を必要とします。いちばん手軽なのはDockerで、`--pid=host --privileged` を付けて `otel/ebpf-instrument` を起動すれば、同じホストで動いているアプリをそのまま観測できます。Kubernetesでは、各ノードに1つずつ置くDaemonSetとして動かす形が代表的です。`hostPID: true` を付ければ、ノード上の全プロセスを1つのOBIが観測します。OpenTelemetry Collectorに組み込むためのreceiverも用意されています。

具体的な設定と、そこから何が見えるのかは次章で扱います。設定項目の網羅は[公式ドキュメント](https://opentelemetry.io/docs/zero-code/obi/)に譲ります。

## 2つの計装経路

OBIの計装は、`SUPPORT_MATRIX.md` にあるとおり2つのカテゴリに分かれます。

一つは**ネットワークレベルのプロトコル計装**で、こちらは言語に依存しません。接続の確立や送受信といったカーネル内のソケット処理に、kprobeやソケットフィルタでフックを置き、流れるバイト列をHTTP/1.1、HTTP/2、gRPC、MySQL、PostgreSQL、Redis、Kafkaなどとして解釈します。アプリが何語で書かれていても、ソケットを通る限り観測できます。TLSで暗号化された通信も、OpenSSLの共有ライブラリの関数にuprobeを置いて、暗号化される前と復号された後の平文を読み取ります。

もう一つが**ランタイムやライブラリのレベルの計装**で、こちらは対象の環境ごとに個別の実装が要ります。RubyやPython、Node.jsに対しても、ランタイム内部の関数にフックを置いて実行の文脈を追う実装があります。ただしライブラリレベルの関数計装を持つのはGoだけです。`net/http` と `database/sql` はGo 1.17以降、`google.golang.org/grpc` は1.40以降、というようにサポート範囲がバージョン単位で決まっています。本書が扱う4つの難所は、すべてこの後者の経路で起きるものです。

![OBIの2つの計装経路](/images/20260911-obi-two-paths.png)
*図2: 矢印は分類の枝分かれを表す。プロトコル計装は言語に依存しない。ランタイムやライブラリのレベルの計装は対象ごとの実装が要り、そのうちライブラリの関数を狙う経路を持つのはGoだけである。*

プロトコル計装だけでも所要時間やステータスコードは取れます。それでもGoに対して関数レベルまで踏み込むのは、ソケットに現れない情報があるからです。たとえばリクエストを処理しているgoroutineの系譜（難所4）はソケットからは見えませんし、直列化前の構造体から値を読めれば、プロトコルの解釈に頼らず正確な値が取れます。

## リポジトリの構成

難所の章では、OBIのソースコードを繰り返し引用します。どこに何があるのか、主要な区画を挙げておきます。

| 場所 | 役割 |
|---|---|
| `bpf/` | カーネル側で動くeBPFプログラムのCソース |
| `bpf/gotracer/` | Goバイナリの関数計装（本書の主役） |
| `bpf/generictracer/` | 言語非依存のプロトコル計装 |
| `bpf/tpinjector/` | コンテキスト伝搬のヘッダ注入（難所4の第2経路） |
| `pkg/` | ユーザー空間側のGoコード |
| `pkg/internal/goexec/` | GoバイナリのELF解析とオフセット解決（難所1と3の主役） |
| `pkg/ebpf/` | eBPFプログラムのロードとアタッチ、リングバッファの読み取り |
| `pkg/export/` | OTLPとPrometheusへのエクスポート |
| `cmd/obi/` | 本体バイナリのエントリポイント |

要するに、カーネル側（C）が `bpf/`、ユーザー空間側（Go）が `pkg/` です。難所の章で引用するファイルは、ほぼすべて `bpf/gotracer/` と `pkg/internal/goexec/` と `pkg/ebpf/` のどれかに入っています。

## この章から難所へ持っていくもの

- OBIは「発見→ELF解析→ロードとアタッチ→イベント収集→エクスポート」というパイプラインで動く独立したプログラムである。
- 計装経路は2つあり、言語非依存のプロトコル計装と、ランタイムやライブラリのレベルの計装に分かれる。後者のうちライブラリの関数を狙う経路を持つのはGoだけで、4つの難所はすべてそこで起きる。
- カーネル側のCコードは `bpf/`、ユーザー空間側のGoコードは `pkg/` にある。
