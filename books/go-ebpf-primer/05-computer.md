この章から6章までは前提パートです。eBPF計装の難しさは、プログラムが動く仕組みの細部から出てきます。まずメモリ、CPU、レジスタ、ポインタを順に押さえ、最後にその集大成として、構造体がメモリにどう置かれるかを確かめます。Goの基本的な文法が読めれば追える範囲にとどめました。

各節に、手元のGoで確かめられる小さなコードを置いてあります。読むだけでも筋は追えますが、一度自分で実行しておくと、難所の章で出てくる実験がすべて「この章でやったことの応用」になります。

## メモリとアドレス

コンピュータの中では、すべての情報が0か1かの**ビット**（bit）で表されます。ビットを8個まとめたものが**バイト**（byte）で、1バイトは0から255までの256通りの値を表せます。

**メモリ**は、このバイトを一列に並べた巨大な棚です。棚のマスひとつひとつに通し番号が振られていて、この番号を**アドレス**（番地）と呼びます。CPUはメモリの中身を「アドレス何番のバイト」という指名で読み書きします。名前で呼ぶ仕組みはメモリにはありません。あるのは番号だけです。

1バイトでは0から255までしか表せないので、大きな値は連続する複数のバイトを使って表します。Goの `int` は8バイト、つまり棚の連続する8マスを占めます。

![メモリは番地の付いたバイトの列](/images/20260820-memory-byte-band.png)
*図1: 上の帯がメモリで、1マスが1バイト。マスの下の数字がアドレスを表す。8バイトの `int` 変数は連続する8マスを占め、変数の「アドレス」とはその先頭のマスの番地を指す。*

このことはGoから確かめられます。`unsafe.Sizeof` は値が占めるバイト数を、`fmt.Printf` の `%p` は変数のアドレスを印字します。

* [Go Playgroundで実行する](https://go.dev/play/p/H7NU6_J67ps)

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	var b byte = 200
	var n int = 300
	fmt.Println(unsafe.Sizeof(b), unsafe.Sizeof(n))
	fmt.Printf("bのアドレス: %p\n", &b)
	fmt.Printf("nのアドレス: %p\n", &n)
}
```

```
1 8
bのアドレス: 0x3dcdc86d8078
nのアドレス: 0x3dcdc86d8070
```

`byte` は1バイト、`int` は8バイトです。アドレスとして印字された `0x3dcdc86d8078` のような値は、実行するたびに変わります。大事なのは個々の値ではなく、アドレスがただの数値だということです。

`0x` で始まるこの表記は**16進数**です。0〜9のあとにa〜fを続けた16種類の文字で数を書く方式で、2桁でちょうど1バイト（256通り）を表せるため、アドレスやメモリの中身はほぼ常に16進数で書かれます。本書でも `0x49e1c0` のような数値が繰り返し出てきますが、16進数の計算はしません。「番地を表す数値が16進で書いてあるだけ」と読めれば足ります。

:::message
なぜ10進数ではなく16進数を使うのでしょうか。10進数の1桁はビットの区切りと合わないため、たとえば「この値の下位8ビット」がぱっと読み取れません。16進数なら1桁が4ビット、2桁が1バイトにきれいに対応するので、バイト単位で区切って読めます。`0x3dcdc86d8078` なら、下2桁の `78` が最後の1バイトです。
:::

## 命令の実行とPC

プログラムの本体は、**命令**の列です。命令とは「この2つの値を足せ」「この番地から値を読め」のような、CPUにできる最小単位の指示のことです。

CPUにどんな命令があるかは、CPUの設計、つまり**アーキテクチャ**ごとに**命令セット**という形で決まっています。本書で扱うamd64と、Apple SiliconやAWS Gravitonで使われるarm64では、命令セットは別物です。同じGoのソースコードでも、どちらのアーキテクチャに向けてビルドするかで、生成される命令の列は変わります。あとの章で登場するCALLやRETも、この命令セットの中の命令です。

命令そのものも、データと同じようにメモリに置かれます。命令の列がメモリに並んでいて、命令ひとつひとつにアドレスがあります。この点は本書の全体に関わります。「関数にフックを置く」といった操作は、最終的にはすべて「この命令アドレスで何かをする」という指定に行き着くからです。

CPUの仕事は単純な繰り返しです。いま実行すべき命令のアドレスを覚えておき、その番地から命令を取ってきて（フェッチ）、意味を解釈し（デコード）、実行する。終わったら次の命令のアドレスへ進んで、同じことを繰り返す。この「いま実行すべき命令のアドレス」を覚えている場所を **PC**（プログラムカウンタ）と呼びます。

![CPUは命令を1つずつ実行する](/images/20260820-fetch-execute-loop.png)
*図2: 上から下へ時間が進む。PCが指す番地の命令を取ってきて実行し、PCは次の命令の番地へ進む。ジャンプ命令はこのPCを別の番地に書き換えることで実現される。*

命令の実物は、逆アセンブルのやり方を扱う4章で見ます。ここでは「命令はメモリに並んでいて、PCがいまの位置を指している」というモデルだけ持って先へ進みます。

## レジスタ

CPUはメモリの中の値をその場で計算しているのではありません。値をいったんCPUの中の小さな入れ物に読み込み、そこで計算し、必要なら書き戻します。この入れ物が**レジスタ**です。計算に使う汎用レジスタは16本で、1つの大きさは64ビット（8バイト）。メモリより桁違いに速い代わりに、桁違いに少ないです（ほかに浮動小数点用などのレジスタ群もありますが、本書には登場しません）。

本書で扱うCPUはamd64（64ビットのx86系）で、汎用レジスタには `RAX`、`RBX`、`RCX` などの名前が付いています。ほかに特別な役割のレジスタが2つあります。ひとつは前節で見たPC、もうひとつはスタック（関数呼び出しのための領域。3章と5章で扱います）の先端を指す `SP` です（それぞれ正式には `RIP`、`RSP` という名前ですが、Goのツール群の表記に合わせます）。

もうひとつ表記の注意があります。CPUのマニュアルやeBPF側の文書は64ビットのレジスタを `RAX` と書き、Goのツールは同じものを `AX` と書きます。以降の出力で両方の表記が出てきますが、指しているものは同じです。

![CPUとレジスタ](/images/20260820-cpu-registers.png)
*図3: 矢印はデータの移動方向を表す。計算はレジスタの上で行われ、メモリは必要なときだけ読み書きされる。*

「関数の引数をレジスタで渡す」という話が難所2で出てきます。それは、呼び出し元が値を `RAX` や `RBX` に入れ、呼び出し先がそこから読む、という取り決めのことです。メモリを経由しないので速く、外から覗く側には見つけにくくなります。

## ポインタ

アドレスはただの数値なので、変数に入れて持ち運べます。アドレスを値として持つ変数が**ポインタ**です。

Goでは `&x` で変数 `x` のアドレスを取り、`*p` でポインタ `p` の指す先の値を読みます。さらに `unsafe.Pointer` と `uintptr` を使うと、アドレスをただの整数として取り出せます。

* [Go Playgroundで実行する](https://go.dev/play/p/Hr7xKAlgfFm)

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	x := 42
	p := &x
	fmt.Printf("xの値: %d\n", x)
	fmt.Printf("xのアドレス: %p\n", p)
	fmt.Printf("pが指す先の値: %d\n", *p)
	fmt.Printf("アドレスをただの数値として見る: %d\n", uintptr(unsafe.Pointer(p)))
}
```

```
xの値: 42
xのアドレス: 0x18eef8586008
pが指す先の値: 42
アドレスをただの数値として見る: 27414647824392
```

最後の行の `27414647824392` は、その上の `0x18eef8586008` と同じ数を10進で書いただけのものです。ポインタの「指す」という言葉の実体は、この数値です。

![ポインタは番地を値として持つ](/images/20260820-pointer-and-address.png)
*図4: 矢印は参照を表す。変数 `p` が保持しているのはアドレスという数値であり、その数値が `x` の置かれたマスの番地と一致しているとき「pはxを指している」と言う。*

`unsafe.Pointer` と `uintptr` は、通常のアプリケーションで書く必要のあるものではありません。本書でこの2つを使うのは、アドレスを数値として印字して比べるため、つまり観察のためだけです。難所1では、この2つで「変数のアドレスが実行中に変わる」瞬間を観察します。

## 構造体はメモリ上でどう並ぶか

この章の締めくくりに、ここまでの内容を使って構造体を見ます。構造体は、フィールドが宣言順にメモリへ並んだものです。ただし詰めて並ぶとは限りません。8バイトの値は8の倍数の番地から始まる、といった制約があるので、あいだに詰め物（パディング）が入ります。

フィールドが構造体の先頭から何バイト目にあるか、という数を**フィールドオフセット**と呼びます。Goでは `unsafe.Offsetof` で取り出せます。

* [Go Playgroundで実行する](https://go.dev/play/p/9lg2L_G44bw)

```go
package main

import (
	"fmt"
	"unsafe"
)

type record struct {
	flag  bool
	count int64
	id    int32
}

func main() {
	var r record
	fmt.Println("flag :", unsafe.Offsetof(r.flag))
	fmt.Println("count:", unsafe.Offsetof(r.count))
	fmt.Println("id   :", unsafe.Offsetof(r.id))
	fmt.Println("全体 :", unsafe.Sizeof(r))
}
```

```
flag : 0
count: 8
id   : 16
全体 : 24
```

`flag` は1バイトなのに、`count` は1ではなく8から始まっています。8バイトの `int64` を8の倍数の番地に置くため、あいだの7バイトが詰め物になったからです。末尾にも、構造体全体の大きさを8の倍数にそろえる詰め物が入っています。

![フィールドの並びとパディング](/images/20260820-struct-padding.png)
*図5: この図に矢印はない。`record` 構造体の24バイトをマスで表した。フィールドの間と末尾に入った詰め物のマスには、どのフィールドの値も入っていない。*

大事なのは、コンパイルしたあとにフィールド名が残らないことです。実行中のメモリにあるのはバイト列とアドレスだけです。`r.count` と書けるのはソースコードの世界の話で、外から同じ値を読むには「構造体の先頭から何バイト目か」を知っていなければなりません。

![ソースの構造体と、メモリのバイト列](/images/20260820-struct-layout.png)
*図6: 矢印は変換の向きを表す。左のソースにあるフィールド名は右のメモリには残らず、バイト位置だけが残る。*

名前が消えるなら、デバッガはなぜ `r.count` を名前で表示できるのでしょうか。この答えは4章のDWARFの節で出てきます。そして、外部の計装ツールがこの「何バイト目か」をどうやって知るのかが、難所3の主題になります。

## この章で各難所に関係する知識

- メモリは番地付きのバイトの列で、アドレスはただの数値である。ポインタはその数値を値として持つ。
- 命令もメモリに並んでいてアドレスを持ち、PCがいま実行中の位置を指す。引数の受け渡しにはレジスタが使われることがある。
- 構造体のフィールド名はコンパイル後に消え、バイト位置（オフセット）だけが残る。

## 確認問題

1. `type pair struct { a int32; b int64 }` の `unsafe.Offsetof(p.b)` と `unsafe.Sizeof(p)` はいくつになるでしょうか。予想してから手元で確かめてください。
2. この章の最初のコードで、`b` と `n` の宣言の順番を入れ替えると、印字される2つのアドレスの関係はどうなるでしょうか。実行して確かめてください。

:::details 解答
1. `b` は8バイトなので8の倍数の番地に置かれ、`Offsetof(p.b)` は8、`Sizeof(p)` は16になります。`a` の後ろに4バイトの詰め物が入ります。
2. アドレスの具体的な値は実行ごとに変わりますが、2つの変数が近い番地に並ぶことは変わりません。どちらが高い番地になるかはコンパイラの配置しだいで、宣言順と一致するとは限りません。
:::
