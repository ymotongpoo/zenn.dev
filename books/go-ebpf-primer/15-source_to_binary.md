title: "ソースコードが実行ファイルになるまで"
---

2章で、命令はメモリに並んでいてアドレスを持つ、と述べました。ではその命令の列はどこから来るのでしょうか。答えは実行ファイルです。書いたソースコードが実行ファイルになるまでの変換と、できあがったファイルの中身を、この章でたどります。

扱うのは3つです。機械語を人が読める形に戻す `go tool objdump`、名前とアドレスの対応表を覗く `go tool nm`、そして実行ファイルの中がどう区分けされているかという知識。どれも難所の章で使い続けます。

## ソースから機械語へ

Goのソースをビルドすると、機械語の命令が並んだバイナリができます。**機械語**とは、2章で見た「CPUにできる最小単位の指示」をバイト列で表したものです。命令は先頭から順に置かれ、1つずつにアドレスがあります。実行とは、`PC` が指すアドレスの命令を取り出して実行し、`PC` を進める、という繰り返しです。

`main.go` に書いた関数は、この変換のどこかで「命令の列と、その置き場所のアドレス」になります。関数の名前や変数の名前は、機械語の世界には基本的に持ち込まれません。

![ソースから機械語へ、そしてシンボル](/images/20260820-source-to-machine.png)
*図1: 実線の矢印は変換の向きを表す。破線はシンボルテーブルが名前からアドレスを引く参照で、変換ではない。*

## 逆アセンブル

機械語のバイト列を人が読める命令の表記に戻す作業が**逆アセンブル**です。Goには `go tool objdump` が付属しています。

先に読み方の構えを決めておきます。本書の目的にアセンブリを書く技能は要りません。逆アセンブルの出力が出てきたら、矢印や注釈を付けた行だけを読んでください。それ以外の行は読み飛ばして構いません。

小さな関数で試します。`//go:noinline` は、コンパイラに関数を展開させず呼び出しとして残させる指示で、理由は5章で説明します。

```go
package main

import "fmt"

//go:noinline
func double(n int) int {
	return n * 2
}

func main() {
	fmt.Println(double(21))
}
```

ビルドして `main.double` を逆アセンブルします。以下は `GOOS=linux GOARCH=amd64` でビルドしたバイナリの出力です。手元がmacやWindowsでも、この2つの環境変数を付けてビルドすれば同じものを観察できます。

```
$ GOOS=linux GOARCH=amd64 go build -o demo main.go
$ go tool objdump -s 'main\.double$' demo
TEXT main.double(SB) .../main.go
  main.go:7   0x49e180   4801c0   ADDQ AX, AX   ← n*2 の計算
  main.go:7   0x49e183   c3       RET           ← 関数から戻る
```

列は左から、ソースの行番号、命令のアドレス、機械語のバイト列、人が読める命令の表記です。`n * 2` というGoの1行が、`ADDQ AX, AX`（`AX` を自分自身に足す、つまり2倍する）という1命令になり、`RET` で関数から戻っています。

バイト列の列に注目してください。`4801c0` の3バイトと `c3` の1バイトで、命令の長さがそろっていません。しかもバイト列そのものには「ここからここまでが1つの命令」という区切りが書かれていません。逆アセンブラは先頭から順に1命令ずつ解釈していくしかありません。この性質は1つ目の難所で、OBIのコードとして現れます。

![バイト列には命令の区切りが書かれていない](/images/20260820-disassemble-boundaries.png)
*図2: 矢印は解釈の進む向きを表す。同じ4バイトの列も、先頭から順に解釈して初めて「3バイトの命令と1バイトの命令」に分かれる。途中のバイトから読み始めると別の解釈になってしまう。*

## シンボルテーブル

名前は機械語に持ち込まれないと書きましたが、バイナリには名前とアドレスの対応表が別に入っています。**シンボルテーブル**です。さきほどの出力にあった「`main.double` はアドレス `0x49e180` から始まる」という情報がここにあり、`go tool nm` で覗けます。

```
$ go tool nm demo | grep 'main\.double'
  49e180 T main.double
```

`go tool objdump` に関数名を渡して該当部分だけを逆アセンブルできたのも、この表があるからです。外から「この関数の入口にフックを置きたい」と考えたとき、名前からアドレスを引く最初の手がかりも、この表になります。

## 静的リンクと動的リンク

コンパイルはソースの部品（Goならパッケージ）ごとに行われます。部品ごとにできた機械語を1つの実行ファイルへ結合し、各関数の最終的な置き場所のアドレスを決める工程が**リンク**で、これを行うプログラムを**リンカ**と呼びます。

ライブラリの結合には2つの方式があります。**静的リンク**は、使うライブラリの機械語を実行ファイルの中へ丸ごと取り込みます。**動的リンク**は、ライブラリを**共有ライブラリ**という別ファイルのまま置いておき、実行時に結び付けます。Cのプログラムの典型は後者で、たとえば標準Cライブラリ（libc）の関数の機械語は実行ファイルの外にあり、そのアドレスは実行時に決まります。

Goのリンカは既定で静的リンクを選びます。それが計装する側に何をもたらすかは、6章で見ます。

![静的リンクされたGoバイナリと動的リンク](/images/20260820-static-link.png)
*図3: 矢印は依存の向きを表す。Cのプロセスは実行時に共有ライブラリへの依存を解決するが、Goのバイナリはその段を持たない。*

## ELFのセクション

Linuxの実行ファイルは**ELF**という形式です。中はセクションに分かれていて、機械語は `.text`、定数は `.rodata`、さきほどのシンボルテーブルは `.symtab` に入ります。

Goのバイナリには、さらにGo固有のものが2つ入ります。アドレスから関数名と行番号を引くための表 `.gopclntab` と、Goの版と依存モジュールの一覧が書かれたビルド情報のブロブです。Goランタイム自身が、パニック時のスタックトレースを組み立てるために `.gopclntab` を読みます。

![ELFバイナリの中身と、それを読む側](/images/20260820-elf-sections.png)
*図4: 矢印は読む側から読まれるセクションへ向かう。誰が何を必要とするかを表しており、データの流れではない。*

## DWARF

2章の終わりに、構造体のフィールド名はコンパイル後に消える、と述べました。それならデバッガはなぜ `r.count` を名前で表示できるのでしょうか。

答えは、コンパイラが**DWARF**というデバッグ情報をELFの `.debug_` で始まるセクション群に書き残しているからです。DWARFには、型の定義、フィールドの名前とオフセット、命令アドレスとソース行の対応が入っています。デバッガはこの表を引いて、バイト列の世界とソースの世界を突き合わせています。

![DWARFはソースとメモリを突き合わせる表](/images/20260820-dwarf-field-mapping.png)
*図5: 矢印は参照を表す。実行中のメモリにはバイト列しか無いが、DWARFが「この型のこのフィールドは先頭から何バイト目」という対応を持っているので、デバッガは名前で表示できる。*

デバッガに便利なものは、外から覗く計装ツールにも便利です。計装ツールは、関数の位置を知るために `.gopclntab` かシンボルテーブルを、フィールドの位置を知るためにDWARFを、版を知るためにビルド情報を読みます。

ただしDWARFやシンボルテーブルは、プログラムの実行そのものには要りません。ビルド時に `-ldflags="-s -w"` を付けると `.symtab` とDWARFが落ち、ファイルは小さくなります。それで計装に何が起きるかは、13章で確かめます。

## この章から難所へ持っていくもの

- 機械語のバイト列には命令の区切りが書かれておらず、先頭から順に解釈するしかない。
- 関数のアドレスは、シンボルテーブルか `.gopclntab` を引けば名前から特定できる。
- フィールド名とオフセットの対応はDWARFにだけ残っていて、`-s -w` で消せる。

## 確認問題

1. 適当なGoプログラムをビルドし、`go tool objdump -s 'main\.main$'` で `main.main` を逆アセンブルして、`RET` 命令がいくつあるか数えてください。
2. `go tool nm` の出力で、自分が書いた関数（`main.` で始まるシンボル）はいくつありますか。書いたはずの小さな関数が見当たらない場合、何が起きたと考えられますか（ヒント: 5章で扱います）。

:::details 解答
1. プログラムによりますが、1つとは限りません。複数ある場合に「すべての `RET`」が問題になる理由は、難所1で扱います。
2. 小さな関数はインライン展開されて、呼び出しごと消えていることがあります。展開された関数は独立した機械語を持たないため、シンボルテーブルにも現れません。詳しくは5章で見ます。
:::
