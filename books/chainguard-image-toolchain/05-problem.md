---
title: "Dockerfileが抱える再現性の問題"
---

melangeとapkoが解決しようとしている課題を先に確認しておきます。多くのチームが日常的に書いているDockerfileには、再現性、攻撃対象領域、SBOMの正確さという3つの点で構造的な弱さがあります。

## ビルド時点のリポジトリ状態に依存する

典型的なDockerfileは次のような`RUN`命令でパッケージをインストールします。

```dockerfile
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y curl ca-certificates
```

このイメージを1年後に同じDockerfileから再ビルドすると、`apt-get update`が参照するパッケージリポジトリの状態はビルドのたびに変わっています。ベースイメージのタグを固定していても、パッケージのバージョンはリポジトリ側のミラーが持つ最新版へと変わってしまいます。結果として、同じDockerfileから毎回ビットレベルで同一のイメージを得ることはできません。パッケージのバージョンをピン留めすれば緩和できますが、依存パッケージの依存パッケージまで含めてすべてピン留めするのは現実的ではなく、大半のDockerfileはこの問題を放置しています。

## 命令の自由度が攻撃対象領域を広げる

`RUN`は任意のシェルコマンドを実行できます。この自由度は開発者にとって便利な反面、イメージの中身について何が起きたのかを機械的に把握することを難しくします。`curl | sh install.sh`のようなパターンでインターネットから取得したスクリプトをそのまま実行するDockerfileは珍しくありませんが、この時点でビルドプロセスの検証可能性は失われます。

加えて、Ubuntuやdebianのような汎用ディストリビューションをベースにすると、アプリケーションの実行に不要なシェルやパッケージマネージャー、各種ユーティリティが同梱されます。これらは実行時に使われなくても、脆弱性が見つかればスキャンツールに検出され、パッチ適用の対象になります。攻撃者にとっても、シェルが使えるコンテナは侵入後の足がかりを得やすくなります。

## SBOMを後から正確に組み立てるのは難しい

[SBOM](https://www.cisa.gov/sbom)（Software Bill of Materials、ソフトウェア部品表）は、イメージに含まれるパッケージとそのバージョンの一覧です。近年はソフトウェアサプライチェーンの透明性を確保する目的で、SBOMの提出を求める組織が増えています。

Dockerfileから作られたイメージのSBOMを作る場合、一般的にはビルドが終わった後のイメージのファイルシステムをスキャンして、パッケージマネージャーのデータベース（`dpkg`や`apk`のデータベースファイルなど）や、バイナリに埋め込まれたバージョン文字列から推測する手法が使われます。たとえば[Syft](https://github.com/anchore/syft)の[binary cataloger](https://github.com/anchore/syft/blob/main/syft/pkg/cataloger/binary/classifiers.go)は、バイナリのファイル名パターンと、ファイル内容中に含まれる既知の文字列パターン（例えばRubyの`ruby 3.4.0dev (...)`のような埋め込み文字列）を正規表現でマッチさせ、そこからパッケージ名やバージョンを推測しています。この方法はビルドプロセスの外側から行う後付けの推測であるため、`RUN`命令の中でソースからコンパイルしたソフトウェアや、パッケージマネージャーを経由せずに配置したバイナリを正確に捕捉できるとは限りません。

## melangeとapkoのアプローチ

melangeとapkoは、この3つの課題に対してビルドプロセスそのものを設計し直すことで応えます。melangeはビルドの各手順を宣言的なパイプラインとして記述し、パッケージのビルド時点でSBOMの断片を生成してパッケージ内に埋め込みます。apkoは`RUN`に相当する任意コマンドの実行を許さず、APKパッケージの組み合わせだけでイメージを構成することで、ビルドプロセス自体を決定的にします。次章ではまず、この2ツールが主要な材料として使うWolfiというディストリビューションを確認します。
