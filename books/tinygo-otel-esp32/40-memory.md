ESP32-S3の内部SRAMは416KBで、サーバーのメモリと比べると桁が4つ以上違います。そのため、マイコンでテレメトリーを送るときに最初に心配になるのはメモリの量です。実際に測ってみると、本書のデバイスではメモリの量は足りていました。問題になったのは、送信のたびにヒープを使い捨てる量と、goroutineのスタックの大きさです。この章では、実機で測った値をもとに、ヒープ、Wi-Fiドライバの領域、スタックの順に見ていきます。

## メモリの量

TinyGoが使えるDRAMは425,984バイト（416KB）で、そのうちヒープの上限は298,287バイトです。残りは、グローバル変数のような静的な領域とメインのスタックが占めます。実機のデバイスが自分で報告したヒープの値は次のとおりでした。

| 項目 | バイト数 | DRAM比 |
| --- | ---: | ---: |
| TinyGoが使えるDRAM | 425,984 | 100% |
| ヒープの上限 | 298,287 | 70% |
| GC後のヒープ（メトリクスのみ） | 約124,000〜179,000 | 29〜42% |
| GC後のヒープ（3シグナル） | 約204,000〜206,000 | 48% |

GCの直後に残っているヒープは、プログラムが実際に保持しているデータの量にあたります。メトリクス、ログ、トレースの3つのシグナルを送る現行版でも、この値はDRAMの半分以下です。ヒープの上限までは、まだ9万バイトほどの余裕があります。

ただし、ヒープの使用量を時系列で見ると、余裕があるようには見えません。送信のたびに使用量が増え続け、上限に近づいたところでGCが走って下がる、鋸の歯のような形の繰り返しです。TinyGoのGCは、ポインタらしく見える値をすべてポインタとみなす保守的なGCで、ヒープの空きがなくなって確保に失敗したときに回収を始めます。そのため鋸の歯の上端はヒープの上限に貼り付き、上端だけを見るとメモリが足りないように見えてしまいます。プログラムが保持している量を表すのは下端の値です。

## 使い捨ての確保

鋸の歯の傾きを決めるのは、1回の送信でヒープに確保して、そのまま捨てるバイト数です。本書ではこの量を**churn**（使い捨ての確保）と呼びます。churnが大きいほどGCの間隔は短くなり、GCが止める時間の分だけ送信の周期が乱れます。

最初の実装では、1回の送信でヒープが8,272バイト増えていました。値が毎回きれいに同じだったのでリークを疑いましたが、GCが走るとヒープは元の水準に戻っていたので、増えた分はすべて捨てられたデータです。8,272バイトの出どころは2つありました。

1つ目は、送信のたびにTCPの接続を張り直していたことです。Wi-Fiドライバの[espradio](https://github.com/tinygo-org/espradio)が使うTCP/IPスタックの[lneto](https://github.com/soypat/lneto)は、接続を張るたびに送信用のバッファ（TxBuf）4,096バイトと受信用のバッファ（RxBuf）1,024バイトを確保します。これに待ち行列や接続のラッパーが加わった分が、送信ごとに捨てられていたわけです。接続を張ったまま使い回すようにすると、1回あたりの増加は4,816バイトに下がりました。接続を使い回すにはHTTPの応答を最後まで読み切る必要があり、その要件は7章で扱っています。

2つ目は、[`encoding/json`](https://pkg.go.dev/encoding/json)の`json.Marshal`です。`json.Marshal`は内部のバッファにエンコードしたあと、結果を新しいスライスにコピーして返します。

```go
buf := append([]byte(nil), e.Bytes()...)
```

APIの形が結果のスライスを返す以上、呼ぶたびに新しい領域が確保されるのは避けられません。そこで、`io.Writer`に書き込む`json.Encoder`を使い、書き込み先の`bytes.Buffer`を1つだけ作って使い回すようにしました。

```go
// json.Marshal ends with append([]byte(nil), ...), so it allocates a new
// buffer on every call. json.Encoder writes into an io.Writer instead,
// which lets one buffer be reused for the life of the program. Measured
// on M5Stack CoreS3: this removes 4,816 bytes of heap churn per export.
buf *bytes.Buffer
enc *json.Encoder
```

`json.Encoder`の`Encode`は末尾に改行を足すので、送るバイト数をCollectorが解釈する内容と一致させるために、最後の改行を削ってから返します。この変更で、1回あたりの増加は688バイトになりました。

その後、応答の読み切りと部分的な成功の解析（7章）、ログとトレースの送信（10章）を足したので、現行版のchurnは再び増えています。

| 実装 | 1回の送信でのヒープの増加（バイト） |
| --- | ---: |
| 送信ごとに接続を張り、`json.Marshal`を使う | 8,272 |
| 接続を使い回す | 4,816 |
| さらにバッファを使い回す | 688 |
| 応答の読み切りと部分的な成功の解析を足す（メトリクスのみ） | 800〜848 |
| ログとトレースを足す（現行の3シグナル版） | 2,992 |

メトリクスだけを送る版では、30分の連続稼働で180回の送信のうち176回が、ちょうど800バイトの増加でした。例外の2回は接続を張った時点と一致していて、初回の接続が46,848バイト、Collectorの再起動のあとの再接続が6,944バイトです。GCは約20分に1回走りました。

現行の3シグナル版は、1回の送信の周期でメトリクス、ログ、トレースの3回のPOSTを送り、4本のスパンのIDを16進文字列に変換して組み立てます。そのため1周期あたりの増加は2,992バイトになり、30分の試験では、接続を張り直した2回を除く170回がすべてこの値でした。GCは30分で7回、約5分に1回走り、GC後のヒープは7回とも204KB前後で、増え続けてはいません[^protobuf-churn]。

[^protobuf-churn]: エンコーダを手書きのprotobufにしたメトリクスのみの版は、1回あたり2,752バイトの増加で、JSON版より大きくなっています。手書きのエンコーダはホストのベンチマークで確保が0回なので、応答の解析のようなエンコーダ以外の経路だと見ていますが、原因はまだ調べていません。

churnを減らす作業では、増加量を小さくすることに加えて、毎回同じ値にすることにも意味がありました。増加量が送信ごとに一定であれば、GCの間隔を計算で予測できるからです。どこかで値が変わったら、その送信で何か普段と違う確保が起きたと分かります。

## GCから見えないメモリ

DRAMには、Goのヒープとは別にWi-Fiドライバが使う領域もあります。espradioは、Espressif社が提供するWi-Fiのバイナリ（ブロブ）をリンクして使い、ブロブは固定長のアリーナ（あらかじめ確保した領域）からメモリを取る作りです。このアリーナはGoのGCの管理の外にあるので、`runtime.ReadMemStats`のヒープの値には現れません。

デバイスは、espradioの`ArenaStats`が返すアリーナの使用量と容量を、Goのヒープとは別のメトリクスとして送っています。2つを分けて送っておけば、メモリの問題が起きたときに、Goのコードの問題なのか、Wi-Fiドライバの問題なのかを切り分けられます。実機では、アリーナの使用量は49,144バイト中31,312バイトで、連続稼働の間も変わりませんでした。

## PSRAMを足しても変わらないもの

M5Stack CoreS3は、内部SRAMとは別に8MBのPSRAM（外付けのRAM）を持っています。しかし、TinyGo 0.42.0のESP32-S3向けのリンカスクリプトが扱うのは内部SRAMの416KBだけで、PSRAMを使うコードもありません。ESP32-S3のPSRAMへの対応を進めているのは[PR #5554](https://github.com/tinygo-org/tinygo/pull/5554)です[^psram]。

[^psram]: 執筆時点でPR #5554はマージされていません。PRの説明では、検証済みなのはOPI接続のPSRAMで、QSPI接続は未検証とされています。

PSRAMが使えるようになっても、本書のデバイスの動作は変わらないと考えています。プログラムが保持しているデータは内部SRAMに収まっていて、PSRAMで増えるのは、GCが走るまでに捨てたデータを溜めておける量だけだからです。PSRAMは外部のバスの先にあるので、内部SRAMより遅くもあります。画面のフレームバッファや音声のように、大きな連続領域が要る用途とは事情が違います。

## goroutineのスタック

メモリの量の次に問題になったのは、goroutineのスタックの大きさです。Go本体のgoroutineのスタックは、足りなくなるとランタイムがより大きな領域へコピーして伸ばします。一方TinyGoのgoroutineのスタックは伸びず、goroutineを作るときに固定の大きさで確保されます。その大きさを決めるのはビルド時の`-stack-size`で、ESP32-S3向けのデフォルトは8KBです。

`encoding/json`はGoの値を再帰的にたどってエンコードします。OTLPのメッセージは、`resourceMetrics`の中に`scopeMetrics`があり、その中に`metrics`があり、さらに`sum`と`dataPoints`が続く深い入れ子なので、再帰も深くなります。単発の構造体やスライスを`json.Marshal`に渡しただけでは8KBでも落ちず、OTLPのペイロードを丸ごと渡したときに初めて落ちるので、小さなテストでは見つかりません。

実機で`-stack-size`を変えて、境界を測りました（エンコーダは`encoding/json`、HTTPクライアントは手書き）。

| `-stack-size` | 結果 | 症状 |
| --- | --- | --- |
| 8KB（既定） | 落ちる | `EXCCAUSE = 28 (LoadProhibited)` |
| 12KB | 落ちる | `EXCCAUSE = 28 (LoadProhibited)` |
| 14KB | 落ちる | `fatal error: goroutine stack overflow` |
| 15KB | 動く | |
| 16KB | 動く | 30分の連続稼働を通過 |

境界は14KBと15KBの間にあります。本書のデバイスでは、15KBでは余裕が1KBしかなく、ペイロードが少し増えるだけで再び落ちるおそれがあるので、16KBにしています。

この表で注意が必要なのは、症状が足りなさの程度によって変わることです。14KBでは、TinyGoが`goroutine stack overflow`と報告して止まります。ところが12KB以下では、この報告が出る前に`LoadProhibited`の例外で落ちてしまいます。`LoadProhibited`は、CPUが読み出しを許されていないアドレスを読もうとしたときに起きる例外で、例外の原因を表すレジスタEXCCAUSEの値28がこれを示します。

この違いは、TinyGoがスタックのあふれを検出する仕組みから説明できると考えています。TinyGoは、goroutineのスタックをヒープから確保し、その一番下（低いアドレス）の1ワードに決まった値（カナリア）を書いておきます。goroutineが実行を中断してスケジューラーに戻るときに、この値が書き換わっていないかを調べ、書き換わっていればスタックがあふれたと判断して止める仕組みです[^canary]。検査はgoroutineが中断するときにしか行われないので、それまでの間にスタックがあふれても止まらず、あふれた分はスタックの外側にあるヒープのメモリを上書きします。あふれる量が小さければ、上書きされたメモリが使われる前に検査に達して報告が出ます。あふれる量が大きいと、上書きされたポインタを読んだ時点で`LoadProhibited`になり、検査までたどり着かないというのが筆者の解釈です。

[^canary]: TinyGo 0.42.0の`src/internal/task/task_stack.go`と`task_stack_unicore.go`で確認できます。カナリアを検査するのは`task.Pause`の中だけです。

ここから言えるのは、スタック不足のエラーが出ないからといってスタックが足りているとは言えないということです。`LoadProhibited`で落ちたときは、スタックの大きさを疑う候補に入れておく必要があります。

最後に、`-stack-size`の指定には単位が必須です。`-stack-size=16384`と書くと、TinyGoは`Unrecognized size suffix`というエラーでビルドを拒否するので、`-stack-size=16KB`と書きます。
