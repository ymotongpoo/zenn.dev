# 「なぜGoバイナリへのeBPF計装は難しいのか」新入生読者レビュー

## この記録の前提

- 対象は `articles/20260820-go-ebpf-instrumentation.md` です。
- 読者は、大学の計算機学科に入学し、変数、関数、メモリという語を習い始めた段階を想定しています。OS、コンパイラ、ネットワーク、Goランタイム、分散トレースの知識は前提にしません。
- 目的は記事を初学者向け入門書に作り替えることではありません。実装の細部を読み飛ばしても、4つの難所について「何を観測したいのか」「Goのどの性質が邪魔をするのか」「OBIが何をしているのか」を追える状態を目指します。

## 全体の判定

基礎編から難所へ進む構成と、各節の図は助けになります。とくに、スタック、レジスタ、ELFを先に説明してから再利用する順序は明確です。

ただし、新入生には一度に保持する用語が多く、説明済みの用語同士を結ぶ中間段階が省かれています。前半では個々の定義を追えても、後半のCコードに入るころには「いま何を得るために、どの場所を読んでいるのか」を見失います。現状のまま主題を理解するには、Goを書いた経験に加えて、OS、アセンブリ、HTTP、分散トレースの基礎が要ります。27行目の「Goのコードを書いたことがあれば追える範囲」という案内とは差があります。

改稿後、新入生が次の4文を自分で説明できれば、記事の主題は伝わっています。

1. `uretprobe` は戻り先を書き換えるため、Goランタイムがスタックを移す処理と衝突する。
2. Goは引数を独自の順序でレジスタに置くため、OBIはCPUごとの対応を知る必要がある。
3. コンパイル後の構造体にはフィールド名がないため、OBIはDWARFか版ごとの表からバイト位置を得る。
4. OBIはgoroutineの親子関係を記録し、送信直前のバイト列に `traceparent` を加えて、別プロセスの処理とつなぐ。

## 最優先で直してほしい箇所

### 可動スタックと `uretprobe` の因果

該当箇所は268〜273行目、316〜318行目、図16です。

現状は「ランタイムが自分のポインタを補正するが、`0xTRAMPOLINE` は補正しないので戻り先を解決できない」と説明しています。新入生には、コードの命令アドレスである `0xTRAMPOLINE` を、なぜ新しいスタックのアドレスに合わせて補正する必要があるのか分かりません。図も「補正の対象外」から `unknown caller pc` へ直接進むため、その間の処理が読み取れません。

Goランタイムがスタックを移す際に、戻りアドレスを何のために読むのかを一段追加してください。たとえば、次の順序なら追えます。

1. Goランタイムは、スタック上に積まれた各関数の戻りアドレスを手がかりに、どの関数のフレームかを調べる。
2. 関数が分かると、そのフレームの大きさと、移動後に直すべきポインタの位置が分かる。
3. `uretprobe` はGoの関数を指していた戻りアドレスを、Goバイナリ外のトランポリンへ置き換える。
4. Goランタイムはトランポリンに対応するGo関数の情報を見つけられず、スタックを正しくたどれない。

実際の失敗機構がこの理解で正しいかを、引用済みのGo issueとランタイム実装に照らして再確認してください。少なくとも「コードのアドレスを補正しないこと自体が原因」と読める現在の表現は避け、`unknown caller pc` に至る処理を特定する必要があります。図16も「ポインタ補正の対象外」ではなく、「戻りアドレスからGo関数の情報を検索するが、トランポリンは見つからない」という図にすると疑問が残りません。

### スタックフレームとレジスタABIの見かけ上の矛盾

該当箇所は62〜68行目、149〜155行目、450〜467行目です。

64行目では「フレームには引数とローカル変数が置かれる」と断定し、456行目以降ではGo 1.17から引数をレジスタに置くと説明しています。初学者は、どちらが正しいのか判断できません。

最初の説明を「スタックフレームは関数ごとの作業領域であり、ローカル変数や退避した値が置かれる。引数の置き場所は呼び出し規約によって異なり、後で見る現在のGoは先頭の引数を主にレジスタで渡す」としてください。戻りアドレスはスタックにある一方、引数はレジスタにもあるという区別も、その場で示すと後のABI節へつながります。

図18とアセンブリでは `RAX` と `AX`、`RBX` と `BX` が混在します。同じレジスタを幅の異なる名前で表していることを一文で説明してください。`Add3(1, 2, 3)` の値を図に直接入れ、「1がAX、2がBX、3がCX」と示すと、対応表を暗記せずに読めます。

### 分散トレースと `traceparent` の導入

該当箇所は11〜17行目、853〜880行目です。

冒頭から「分散トレース」「ゼロコード計装」「HTTP」「gRPC」が定義なしで並びます。4つ目の難所ではトレースID、スパンID、`traceparent` が一度に加わります。これらを知らない読者は、ヘッダを書き込む目的を理解できないまま、書き込み方法の説明を読むことになります。

冒頭にサービスAからサービスBを呼ぶ短い例を置いてください。Aで始めた処理とBで続く処理に同じトレースIDを持たせると、二つの記録を一本の流れとして表示できる。その識別情報をHTTPで渡すヘッダが `traceparent` であり、コードを変更せずに追加するのがこの記事のいうゼロコード計装です。この程度で足ります。

857行目付近では、トレース、スパン、トレースID、スパンIDの関係も小さな図か具体的なヘッダ例で示してください。値の各桁の仕様までは要りません。「同じトレースIDを渡し、Bは新しいスパンとして処理を続ける」という関係が必要です。

### 「引数は読めるのに `context.Context` は追えない」という疑問

該当箇所は543〜575行目、875〜888行目です。

2つ目の難所ではレジスタから関数の引数を読めると説明しています。その後、884行目で「外から見ているeBPFにその引数は追えません」と書くため、新入生には矛盾して見えます。

一度の関数呼び出しでレジスタの値を読むことと、`context.Context` が複数の関数やgoroutineを渡るあいだ、その意味と親子関係を追い続けることを分けて説明してください。`context.Context` は単なる数値ではなく、インターフェース値が内部のオブジェクトを参照する構造であり、関数ごとに置かれる引数の位置も異なるため、「一度ポインタを読めば追跡できる」わけではない、と書けばつながります。そのうえで、OBIは値そのものを解読せず、goroutineの生成関係を代わりの手がかりにしている、と続けると4つ目の難所の狙いが明確になります。

### goroutine追跡コードの前に必要な処理の要約

該当箇所は882〜972行目です。

`runtime.newproc1` のCコードには、入口と出口、レジスタ、二つのマップ、三種類のキー、アドレス再利用への対処が含まれます。コードを一行ずつ追う前に目的を見失います。

Cコードの前に、次の擬似コードを置いてください。

```text
goroutineを作り始めたとき:
    作成元goroutineを一時保存する

goroutineを作り終えたとき:
    戻り値から新しいgoroutineを得る
    新しいgoroutine -> 親goroutine をマップへ保存する
```

続く実コードでは、この擬似コードに対応する行だけを先に示し、PID、`pt_regs`、エラー処理、古いエントリの削除は二つ目の抜粋か補足へ分けると理解しやすくなります。`newproc1` が受け取る第2引数を「親goroutine」と呼べる理由と、戻り値が新しい `g` であることも、関数の簡略化したシグネチャで示してください。

### HTTPヘッダ注入の全体像

該当箇所は1020〜1093行目です。

`http.Header`、Goのmap内部、直列化、`Header.writeSubset`、`bufio.Writer`、`bpf_probe_write_user`、`sk_msg` が短い範囲に並びます。図26と図27は処理の位置を示していますが、最終的なHTTPのバイト列を見たことがない読者には、どこへ何を書いているのか分かりません。

最初に、送信直前のHTTP/1.1リクエストを短く示してください。

```http
GET /items HTTP/1.1
Host: service-b
Traceparent: 00-...-...-01
```

その後に、Goの `http.Header` は操作しづらいので、OBIはこの文字列を組み立て終える直前のバッファに一行を追加する、と説明してください。`bufio.Writer.n` は「現在使っているバイト数」であり、文字列の追加後にこの数も増やす必要がある、と続ければCコードの4回の書き込みに対応します。

`sk_msg` は初出で定義してください。「アプリのメモリではなく、カーネルがソケットへ送るデータを扱う位置で、同じヘッダのバイト列を差し込む別経路」と説明すれば十分です。パケットとTCPのバイトストリームを同じものとして扱わないよう、ここでどの単位を変更しているのかも明示してください。

## 次に直してほしい箇所

### 冒頭の用語と二つの計装経路

該当箇所は11〜23行目、230〜239行目です。

13行目の「関数レベルまで踏み込む経路」と「通信のバイト列をプロトコルとして解釈する経路」の違いは、OBIの節まで具体化されません。冒頭で、次の二つを一例ずつ示してください。

- 通信を見る計装は、送受信される `GET /items` のようなバイト列からHTTPだと判断する。
- Goの関数を見る計装は、`net/http` の特定の関数が呼ばれた瞬間に、その引数を読む。

「バイナリ」は、0と1一般ではなく、コンパイル後の実行ファイルを指すことも初出で断ってください。「計装」は、処理時間や呼び出し関係を記録するための観測点を加えること、と短く定義できます。

### ソースから実行までの一本の流れ

該当箇所は25〜108行目です。

ユーザー空間、仮想アドレス、レジスタ、スタックフレーム、機械語、シンボル、ELFが節ごとに説明されています。ただし、これらが一つのプログラムのどの時点に現れるのかは、読者が組み立てる必要があります。

基礎編の冒頭に、次の流れを一枚置いてください。

```text
Goのソースコード
    -> コンパイラが機械語へ変換
    -> ELF形式の実行ファイル
    -> OSがプロセスとしてメモリへ配置
    -> CPUがPCの指す命令を実行
    -> 関数呼び出し時にはレジスタとスタックを使用
```

この図の各箱から既存の節へ案内すれば、用語を別々に暗記せずに済みます。システムコールは、ユーザー空間のプログラムがカーネルの機能を呼ぶための特別な関数呼び出し、と通常のGo関数との違いを添えてください。

### 実験コードにある仕掛け

該当箇所は275〜318行目、335〜383行目、469〜501行目です。

三つの実験は結果が明確ですが、新入生には `//go:noinline`、`unsafe.Pointer`、`uintptr`、深い再帰、`defer` が未説明です。本文の主題とは別の難しさが混ざっています。

各コードの直前に「結果を見やすくするための仕掛け」を二、三文で説明してください。スタック移動の例なら、コンパイラに関数を消されないための `//go:noinline`、スタックを確実に消費する `pad` と再帰、アドレスを数値として比較するためだけの `unsafe` です。通常のアプリケーションで推奨する書き方ではないことも明記してください。

316行目の「`moved` は常に `true`」は、実行環境や将来のコンパイラまで含む断定に見えます。「この記事で使ったGo 1.26.0 linux/amd64では、毎回 `true` になった」のように実測範囲へ限定すると、再現しなかった読者が自分の理解を疑わずに済みます。

### アセンブリ抜粋の読み方

該当箇所は364〜383行目、488〜501行目です。

読者が見るべきなのは、最初の抜粋では二つの `RET`、次の抜粋ではAX、BX、CXだけです。しかし、`CMPQ`、`JBE`、`POPQ`、`LEAQ`、`SB`、`NOSPLIT` も同じ強さで表示されています。

見る行を短く抜き出すか、無視してよい列と命令を明記してください。`LEAQ` は名前からメモリ読み込みに見えるので、この例ではアドレス計算命令を足し算に使っている、と一文必要です。ソースの一つの `return` から二つの `RET` が生じる例では、通常時と `defer` 処理をやり直す経路がいつ選ばれるのかも説明してください。「片方にしか置かないと、どの状況の計測が欠けるか」が分かれば、全 `RET` を探す理由が残ります。

### `g` 構造体、スタック、アドレス再利用

該当箇所は545〜593行目、963〜970行目です。

図20は `g` とスタックの違いをよく示しています。ここに時間軸を一つ足すと、アドレスを識別子にする利点と欠点を同時に理解できます。

```text
時刻1: goroutine A の g が 0x1000 にある
時刻2: A のスタックだけが移動する。g は 0x1000 のまま
時刻3: A が終了する
時刻4: goroutine B の g として 0x1000 が再利用される
```

これにより、「処理中は同じ識別子として使えるが、終了後の古いマップ要素は消す必要がある」という970行目までの話を一度に追えます。`p` は後の説明に使わないため、131行目と549行目では「Goコードを動かすための実行権と待ち行列」程度にとどめるか、補足へ移しても主題は失われません。

### フィールドオフセットがずれる計算

該当箇所は603〜718行目です。

`streamV1` と `streamV2` の例は有用ですが、なぜ `any` が16バイトで、`func()` の追加後に `id` が16から24へ移るのかが説明されていません。構造体を1バイト刻みの帯として描き、各フィールドの大きさとパディングを示してください。オフセットは「構造体の先頭を0番地としたとき、そのフィールドの先頭までに何バイトあるか」と言い換えると、`unsafe.Offsetof` の出力を読みやすくなります。

`internal/transport` に互換性の約束がないという説明では、公開型と非公開の内部型の違いを一文添えてください。ライブラリ利用者に見せる公開APIではないため、開発者は更新時に並びを変えられる。その自由さを、外からメモリ位置で読むOBIが引き受けている、という因果が分かります。

### DWARFと事前計算表の分岐

該当箇所は720〜799行目、803〜849行目です。

図22で二つの経路は分かりますが、DWARFがなぜ正解を持つのかを補ってください。コンパイラがデバッガ向けに「この型のこのフィールドは先頭から何バイト目」という対応を書き残しているため、OBIは目の前のバイナリに合う値を読める、という説明が必要です。

757行目の「1つでも残っていればDWARF経路を諦めます」は、`structMemberPreFetchedOffsets(elfFile, offs)` に取得済みの `offs` を渡しているコードと食い違って見えます。取得済みのDWARF値を捨てるのか、不足分だけ表で補うのかを確認し、正確に書き分けてください。

799行目の「それを保証しているのがこのコメント1行」も疑問が残ります。コメントは対応関係を機械的に保証しません。テストや生成処理が保証しているなら、その仕組みを示してください。人が同じ順序を保つ決まりしかないなら、「コンパイラは検査せず、実装者が保つ必要のある対応関係」と書くほうが、難所の説明として正確です。

### 6段という上限の影響

該当箇所は974〜1018行目です。

検証器が有限の上限を求めることは分かりますが、なぜ上限が6で、7段目で何が起きるのかは曖昧です。6は安全性から導かれた数ではなく、命令量と実際のライブラリで必要な深さを踏まえた実装上の選択だと区別してください。

「7段以上なら必ずトレース全体が消える」わけではなく、現在のgoroutineからトレース情報を持つ祖先までの距離が探索上限を超えた場合に、親のコンテキストを見つけられない、という条件を示してください。見つからなかった送信処理をOBIが新しいトレースとして扱うのか、計装しないのかも記載すると、利用者への影響が分かります。

### 用語の再登場を助ける短い言い換え

ELF、DWARF、`.gopclntab`、ABIInternal、`g` は一度定義してから数百行後に再登場します。初学者は定義の場所を探し直します。再登場時に、次のような短い同格説明を一度だけ添えてください。

- DWARF（型とフィールド位置を含むデバッグ情報）
- `.gopclntab`（命令アドレスからGoの関数名を引く表）
- `g`（goroutine一つを表すランタイム内部の構造体）
- ABIInternal（Go関数が引数を受け渡す内部規約）

末尾に用語集を置くだけでは、本文を読んでいる時点の負荷は減りません。再登場した場所で意味を思い出せる形が適しています。
