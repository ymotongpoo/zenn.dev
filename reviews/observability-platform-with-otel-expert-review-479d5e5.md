## この記録の前提

- 対象は `books/observability-platform-with-otel/` の全10章と `config.yaml` です。
- `research/observability-platform-with-otel.md` を調査台帳として参照し、変動しやすい事項は2026年8月25日に一次情報で再確認しました。

## 総合判定

三本柱の選び方は妥当です。SDKディストリビューションとゼロコード計装を「計装の配布」にまとめ、Collector層、セマンティック規約のガバナンスと並べる構図は、OpenTelemetryの機能一覧をPlatform Engineeringの設計判断へ変換できています。各章も具体的な失敗や依頼から始まるため、導入の推進力があります。とくに00章の分断されたトレース、50章の属性改名、60章の経理とSREから届く質問は、その章で解く問題を読者がすぐ把握できる例です。

技術調査も精度が高く、OpenTelemetry Go、Collector、OBI、otelc、OpAMP、Weaver、GenAIセマンティック規約の2026年8月時点のバージョンとstabilityは、確認した範囲で大筋が合っています。古いOCBの `otelcol_version`、Weaverの非推奨コマンド、OperatorによるGo計装の制約など、誤りやすい事項を先回りしている点も残すべきです。

ただし、現状のまま公開できる初稿ではありません。公開を止める問題は三つあります。80章が未公開のリポジトリと未実測の挙動を完成済みの事実として説明していること、登壇概要と原稿で読者の前提知識が食い違うこと、複数設定ファイルのマージで統制境界を保証できるという設計が成立していないことです。後ろ二つは登壇の主張にも関わります。

スライド原案として見ると、材料は十分にありますが、このまま章を圧縮するとツールの紹介が続く発表になります。登壇で残すべき中心は「誰が何を決めるかを、実行可能な既定値と検査へ移す」という設計です。AIの話は新しい第四の柱ではなく、三本柱を整備した結果として扱う現在の位置づけが適切です。

アプリケーション

### 設定マージでは統制境界を保証できない

該当箇所は `30-collector_build.md` 102〜118行目と `40-collector_fleet.md` 55行目です。

30章は、基盤の `base.yaml` とチームの追記用ファイルを順にマージすれば、「チームは自分のパイプラインを足せるが、共通パイプラインのmemory_limiterやPII削除は外せない」という境界を作れると説明しています。しかし、CollectorとSupervisorの設定は後から読んだ値が先の値を上書きできます。[Supervisorの仕様](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/cmd/opampsupervisor/specification/README.md#notes-on-agentconfig_files-agentargs-and-agentenv)も、後の設定が前の設定を上書きすると明記しています。Supervisorの実装状況では、Collector設定のsanitizationまたはrestrictionも未実装です。

チームのファイルが `service.pipelines.traces.processors` を再定義すれば、リストを差し替えて共通processorを外せます。コンポーネント自体を残しても、pipelineから参照されなければ実行されません。したがって、現在の説明は利便性のための設定合成を、権限境界として扱っています。

統制が必要な値には任意のCollector設定を書かせないでください。次のいずれかで入力面を狭める必要があります。

- チームが指定できる項目を、送信先や追加属性などの型付きパラメーターに限定し、基盤側で最終的なCollector設定を生成します。
- チーム追加用のpipelineを別名で生成し、共通pipelineや必須processorを変更できないポリシーをCIで検査します。
- Supervisorでは `$REMOTE_CONFIG` より後に基盤管理の `compliance_config.yaml` を置きます。ただし後勝ちだけに依存せず、`print-config` で得た実効設定に必須processorと接続先の検査をかけます。
- 自由な拡張が必要なら、信頼境界ごとにCollectorを分けます。チーム管理のCollectorから基盤管理のgatewayへ送り、後段のPII削除や認証をチームが変更できない構成にします。

40章の「前章で設計した境界がそのまま生きる」という一文も、この修正に合わせて書き直す必要があります。ここは三本柱のうち「何をセルフサービスにし、何をプラットフォームが統制するか」を具体化する箇所なので、登壇でも曖昧にできません。

## 優先して直す技術事項

### ロールバックが保証する範囲を限定する

該当箇所は `40-collector_fleet.md` 63〜65行目と `80-reference_implementation.md` 67〜69行目です。

Supervisorの `automatic_config_rollback` が検出するのは、リモート設定を適用した後にCollectorが正常に起動できない状態です。[公式README](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/cmd/opampsupervisor#automatic-remote-configuration-rollback)もこの範囲で説明しています。構文上は正しいが全データをfilterで落とす設定、誤った宛先へ送る設定、認証に失敗する設定、処理量を支えられない設定は、Collectorが起動するため自動ロールバックの対象にならない可能性があります。

「壊れた設定を配ってもテレメトリーは止まらない」という保証は削ってください。保証できるのは「Collectorの起動失敗を検出した場合に、最後に起動できたリモート設定へ戻す」です。運用上の安全性には、canary、Collector自身の送受信件数とexporter失敗率、合成テレメトリーの到着確認、段階展開の停止条件が別に必要です。80章で検証するなら、構文エラーだけでなく、全件dropと不正なexporter認証も失敗シナリオに加えてください。

### 二行の初期化例でエラーを無視しない

該当箇所は `10-sdk_distribution.md` 52〜69行目です。

章の中心となる例は次の二行です。

```go
shutdown, err := otelinit.Setup(ctx)
defer shutdown(ctx)
```

`err` を確認する前に `shutdown` を呼ぶ予約をしており、`Setup` がエラー時にnilを返す契約ならpanicします。常にno-opのshutdownを返す契約にしても、その契約が本文にありません。初期化失敗を無視する設計にも見えます。

「二行」を目標にすると、正しい失敗処理が表示から消えます。次のように、利用者が書く最小の正しい形を示してください。

```go
shutdown, err := otelinit.Setup(ctx)
if err != nil {
    return fmt.Errorf("initialize telemetry: %w", err)
}
defer func() {
    _ = shutdown(context.Background())
}()
```

アプリケーションを起動不能にするか、テレメトリーなしで継続するかは組織の方針です。ディストリビューションはその判断を隠さず、失敗の観測方法も契約に含めるべきです。登壇では「二行」より「exporter、resource、propagatorの判断をアプリから除く」と説明したほうが、本質を保てます。

### GenAI本文のredactionを最後の保証にしない

該当箇所は `60-ai_workload_telemetry.md` 39〜49行目と104〜110行目です。

原稿は、プロンプト本文を記録する判断をチームへ委ね、gatewayでPIIを落とす分担を推奨しています。`gen_ai.input.messages` や `gen_ai.output.messages` は構造化された `any` 型であり、言語が対応しなければJSON文字列にもなります。自然言語、ツール引数、画像や外部ストレージへの参照を含む内容から、Collectorの変換規則だけでPIIと機密情報を漏れなく識別することはできません。

PII削除を保証するように読める表現を避け、次の多層防御へ変更してください。

1. 既定では本文を記録しません。
2. 有効化するサービスはデータ分類と利用目的を登録し、SDK側で許可したフィールドだけを記録します。
3. gatewayのredactionは既知のパターンに対する追加防御として使います。
4. 本文を含むテレメトリーを別pipeline、別テナント、短い保持期間、限定した閲覧権限で扱います。
5. live-checkや結合テストへ、記録してはならない既知データの検査を加えます。

「チームが決める」と「基盤が保証する」の線引きを扱う題材としては有用です。ただし、基盤が保証できるのは保存先、権限、保持期間、既知パターンの削除であり、任意の自然言語から機密情報を完全に除くことではありません。

### AIによる調査精度を検証可能な主張にする

該当箇所は `00-introduction.md` 44〜48行目と `70-ai_driven_operations.md` 21〜50行目、67行目です。

70章は、属性名が揺れるとAIエージェントが半分のデータを見落とし、自信を持って誤報すると断定しています。起こり得る失敗としては妥当ですが、引用されているOpenTelemetryの資料はスキーマやMCPの仕様を支えるものであり、AI障害調査の正答率を支える実証ではありません。「スキーマ統制への投資がAIの調査精度に直接変換される」「データの質で上限が決まる」も、現状では著者の設計仮説です。

主張を弱めるだけでは、この章の価値がなくなります。仮説、機構、検証方法を分けてください。

- 機構として、エージェントが生成するクエリに存在しない属性名が入れば結果が空になり、検索対象を一種類に決めれば別名のデータを除外する、と説明します。
- 失敗例は架空の事故として明記し、`service.name=payment` と `payment-api` の件数差、生成されたクエリ、見落としたスパンを具体的に示します。
- 80章の実験では、同じ事故データに対して、レジストリなし、レジストリだけあり、レジストリと統制済みデータありの三条件で調査結果を比較します。正答率だけでなく、参照した属性、クエリ件数、根拠リンクの有無を記録します。

実測しない場合は「前提条件になる」と断定せず、「誤ったクエリを減らすために、スキーマを参照可能にする」と、保証する機構の範囲へ狭めてください。

### リリースのないGenAI規約を再現可能に取り込む

該当箇所は `60-ai_workload_telemetry.md` 20〜37行目と51〜83行目です。

専用の `semantic-conventions-genai` リポジトリにリリースもタグもないという説明は正確です。同リポジトリには `model/manifest.yaml` があるためWeaverの依存として解決できますが、`main` をそのまま参照すると同じ社内レジストリを後日解決した結果が変わります。

「依存として取り込む」に、コミットSHAを固定する運用を追加してください。社内レジストリには採用したSHA、採用日、上流の `schema_url` を記録し、定期更新PRでdiffを確認します。正式リリースが始まったらタグ固定へ移します。Developmentの規約をガバナンスで扱う、という章の主張を具体的な再現性へ落とせます。

Goの手動計装例も現在の規約への追従方法を十分に示していません。文字列で属性名を書いているため、直前の50章で推奨した生成定数を使ってください。現在のInference spanではエラー時の `error.type` がConditionally Requiredです。`span.SetStatus` だけで終える例は、規約準拠の完成例ではないと明記するか、`error.type` と例外記録を追加します。メトリクスも本文で約束しているため、スパンだけを示すなら「抜粋」と断ってください。

### 生成定数は文字列の使用を禁止しない

該当箇所は `50-semconv_governance.md` 74〜89行目です。

87行目は、生成定数を使えば「属性名のタイポはコンパイルエラーになる」と説明しています。Goの `attribute.String` は任意の文字列を受け取るため、開発者が `attribute.String("com.exmaple.delivery.id", id)` と書いてもコンパイルは通ります。生成定数は手書きする機会を減らしますが、手書きを禁止しません。正しい定数から意味の違う属性を選んだ場合も型検査では検出できません。

効果を「IDEで発見でき、文字列を手書きする必要がなくなる」に限定してください。強制するには、社内ラッパーAPI、静的解析、コードレビュー、live-checkのいずれかが必要です。live-checkで実測を検査する後節につなげれば、「生成で予防し、実測で検出する」という二段の説明になります。

### schema URLと属性変換を一緒に扱う

該当箇所は `30-collector_build.md` 37〜47行目と `50-semconv_governance.md` 101〜118行目です。

原稿は、非推奨属性をgatewayで新しい名前へ書き換え、レジストリの改名情報からtransform設定を生成する案を示しています。しかし、テレメトリーが古いschema URLを名乗ったまま属性だけを新名へ変えると、データとschema URLの対応が一致しません。逆にschema URLだけを新しくしても、ほかの変更をすべて適用した保証が要ります。

属性の書き換えを単独の文字列置換として説明せず、入力のschema URL、適用する変換、出力のschema URLを一組にしてください。公式schemaの変換が使える範囲と、社内レジストリ独自の移行を区別します。移行期間に旧属性と新属性を併記する場合は、どちらを正とし、ダッシュボードをいつ切り替え、いつ旧属性を削除するかも示す必要があります。

### OTLP対応だけではバックエンドを交換できない

該当箇所は `00-introduction.md` 56〜57行目と `80-reference_implementation.md` 39〜49行目です。

「OTLP対応のバックエンドであれば何にでも適用できる」「何に差し替えても成立する」は範囲が広すぎます。OTLPで送信する部分は交換できますが、tail sampling後の保存形式、テナント分離、クエリ言語、exemplarからトレースへの移動、ログとの相関、MCPによる検索、認可はバックエンドごとに異なります。70章でAIがテレメトリーを読む部分は、特にバックエンド固有のツール定義へ依存します。

「三本柱のうち、計装からOTLP送信までの設計はバックエンドに依存しない」と範囲を限定してください。そのうえで、リファレンス実装の交換面をOTLP exporter、認証、テナントルーティング、クエリ用MCPサーバー、結果へのリンク生成に分けます。この表があれば、ベンダー非依存という主張を設計として検証できます。

### 自作OpAMPサーバーを小さく見積もらない

該当箇所は `40-collector_fleet.md` 69〜81行目です。

公式のスタンドアロンOpAMPサーバー製品がなく、opamp-goのexample serverを本番に置けないという整理は妥当です。一方、「自作か商用か」の二択と、「配達だけならコードは驚くほど小さい」という説明は、本番の管理プレーンに必要な仕事を隠します。認証、エージェントID、テナント分離、対象グループ、永続化、監査、HA、段階展開、競合する更新、失効した証明書、サーバー自身のアップグレードが残ります。

80章で作るものは、プロトコルを理解するためのexample serverであり、本番参照実装ではないと明記してください。本番の選択肢は、GitOpsを継続する、管理製品を使う、組織内の既存管理プレーンへOpAMPを実装する、専用の管理プレーンを構築する、の少なくとも四つです。導入判断の節がすでにあるため、規模より変更頻度と必要な機能で選ぶ表へまとめると実務に使えます。

## 次に直す設計と説明

### ParentBasedとtail samplingの流量設計

該当箇所は `10-sdk_distribution.md` 61〜73行目と `30-collector_build.md` 37〜43行目です。

ディストリビューションの既定をParentBasedとし、間引きの主体をgatewayのtail samplingへ寄せる案では、root samplerをAlwaysOnにするとすべてのスパンがアプリからgatewayまで流れます。Go SDKの `AlwaysSample` にも、本番の大量トラフィックでは全リクエストをexportする点への注意があります。tail samplingは保存量を減らしますが、SDK、agent、ネットワーク、gatewayが受ける量は減らしません。

これは誤りではなく、容量の前提が抜けています。低流量ではParentBasedのAlwaysOnとtail sampling、高流量ではhead samplingとの組み合わせ、重要なサービスだけAlwaysOn、緊急時の負荷制御など、どの段階で量を落とすかを示してください。trace IDでgatewayを振り分ける前段も、二段構成図に入れる必要があります。

### Collectorの「信頼性」を条件付きで書く

該当箇所は `30-collector_build.md` 9〜33行目です。

Collectorはバッチ、リトライ、バックプレッシャーを引き受けますが、メモリキューだけならプロセスやノードの停止でデータを失います。agentとアプリが同じノードにいればネットワーク距離は短くなる一方、ノード障害の運命は共有します。gatewayを追加すれば障害点と運用対象も増えます。

「送信の信頼性」を保証ではなく機能として説明し、メモリキュー、永続キュー、再送、容量超過時のdrop、ノード停止時の損失範囲を分けてください。agentとgatewayの二段構成も唯一の標準解ではなく、本書が置く組織規模と要件に対する推奨だと明記します。

### ゼロコード計装の推奨を判断表にする

該当箇所は `20-zero_code_instrumentation.md` 15〜53行目と84〜109行目です。

OBI v0.12.2、otelc v1.1.0、Operatorが注入するGo計装の制約は一次情報と合っています。ただし「CIを握っているプラットフォームではotelcが第一候補」という結論は、本書の推奨であり公式の優先順位ではありません。対応ライブラリ、Goツールチェーンとの互換性、ビルド時間、必要権限、実行時の対象発見、コンテキスト伝播、ロールバック方法で判断が変わります。

eBPF、otelc、手動計装を、コード変更、ビルド変更、特権、対応範囲、得られる属性、重複排除、更新単位で比較してください。スライドではこの表を簡略化し、「プラットフォームが変更できる場所で方式を選ぶ」という判断だけを残せます。

### Weaverの三機能と運用ループを分ける

該当箇所は `50-semconv_governance.md` 74〜110行目です。

check、generate、diffの説明は正確ですが、live-checkを加えると章の中心は三つではなくなります。現在の構成は「中心は3つ」と宣言した後に、実運用で重要なlive-checkが別に出てくるため、読者は機能一覧と運用段階のどちらを覚えるべきか迷います。

機能数を見出しにせず、変更前のcheckとdiff、マージ後のgenerate、実測時のlive-checkという時間順へ並べてください。この順序なら、定義、生成物、実データの三者がずれる場所も分かります。`weaver registry mcp` は同じループではなく、レジストリの別の消費者として60章または70章への接続に残します。

### 二種類のMCPサーバーを図で分ける

該当箇所は `50-semconv_governance.md` 120行目、`70-ai_driven_operations.md` 23〜54行目、`80-reference_implementation.md` 71〜75行目です。

AIエージェントには二種類のアクセスが必要です。`weaver registry mcp` は属性と規約を読むためのサーバーで、Tempo、Prometheus、Lokiなどを検索するMCPサーバーは実データを読むためのサーバーです。現在の文章は離れた段落で両方を説明するため、一つのMCPサーバーがスキーマとデータの双方を提供するようにも読めます。

次の構成を一枚にしてください。

```text
                   ┌─ registry MCP ─ 社内レジストリ
AI調査エージェント ┤
                   └─ telemetry MCP ─ 観測バックエンド
                              │
                              └─ 根拠となるクエリとリンク
```

認可も別です。レジストリを読む権限と本番テレメトリーを読む権限を分け、MCP呼び出し自体のトレースは第三の観測データとして扱います。MCPが「事実上の共通口」という表現には、採用例を一次情報で二、三件示すか、「有力な接続方式」に留めてください。
