## はじめに

AIエージェントにオブザーバビリティの仕事をさせたとき、その最終応答の品質が上がったのか下がったのかを、どうやって知るのでしょうか。

エージェントの最終応答を読んで判断する方法は、早い段階で行き詰まります。正しい応答と、正しく見えるだけの応答が同じ見た目をしているからです。しかも同じ質問に毎回同じ応答が返るわけでもなく、期待する文字列を固定したテストは書けません。

この記事では、[Grafana Assistant](https://grafana.com/docs/grafana-cloud/machine-learning/assistant/)を開発しているチームが公式のエンジニアリングブログに公開した [Building an evaluation loop for Grafana Assistant](https://medium.com/grafana-labs/building-an-evaluation-loop-for-grafana-assistant-9a8690d8662d)（Yasir Ekinci、2026年4月30日）を参考に、AIエージェントの評価方法を考察します。記事で紹介されている評価基盤は社内のものですが、同じ考え方を使った [o11y-bench](https://github.com/grafana/o11y-bench) がオープンソースで公開されています。後半はそのシナリオ定義を読み、実装を確認する流れです。

## TL;DR

AIエージェントの品質は、最終応答だけでは評価できません。実行の過程をシナリオとグレーダーで評価します。事実は決定的なチェックで、結論は基準を分解したLLMの判定で確かめる、という使い分けです。複数回の結果を能力ごとに比較し、AIが提案し、ベンチマークが検証し、人間が決めるループを継続します。

## もっともらしく見える失敗

記事の冒頭に、AIエージェントの評価が難しい理由が書かれています。

> the hardest failures usually aren’t the obvious ones; they’re the ones that look plausible on the surface.
>
> （最も難しい失敗はたいてい明白なものではなく、表面上もっともらしく見えるものである）

具体例も2つ挙げられています。

* 答えは良く書けているのに、間違ったクエリに基づいている。
* パネルは正常に描画されるのに、ユーザーが何かを理解する助けにはなっていない。

どちらも、最終的な応答を読むだけでは見落とすことがあります。

エージェントがタスクに従っているように見えながら、途中のどこかで悪い判断を下していることもあります。しかもシステムは非決定的なので、同じ要求が一度は成功しても、次には失敗することがあります。オブザーバビリティのタスクは答えの形が定まっておらず、複数の手順を踏むことが多いため、この種の失敗はとくに気付かれにくいものです。

そこで評価の対象が変わります。

> For a tool-using agent, the final answer is only part of the behavior. The rest is hidden in the steps that produced it.
>
> （ツールを使うエージェントにとって、最終的な答えは振る舞いの一部にすぎない。残りは、それを生み出した手順の中に隠れている）

見るべきものは、最終的な答えに至るまでの手順全体です。どのツールを呼び、どんな引数を渡し、結果をどう解釈し、次に何をして、結果をどうユーザーに伝えたかまでが対象になります。出力だけを検査する方法では足りません。

## シナリオを仕様として置く

実行の過程を見るために、記事のチームはプロンプトを唯一の基準として扱うのをやめました。代わりにシナリオとグレーダーを書きました。

**シナリオ**は現実のユーザーのワークフローと、成功が何を意味するかを記述します。**グレーダー**は、その成功が実際に起きたかを判定します。判定の根拠には、ツールの引数、クエリの構造、保存されたGrafanaの状態、遷移先のURL、環境から実際に取得できる事実を使います。

記事では、この分離を次のように説明しています。

> The desired behavior is encoded separately from how the implementation achieves it, 
> whether that implementation is the agent itself, its prompt, its routing logic, or the code around it.
>
> （望ましい振る舞いは、実装がそれをどう達成するかとは別に記述される。その実装がエージェント自身であれ、プロンプトであれ、ルーティングのロジックであれ、周辺のコードであれ変わらない）

望ましい振る舞いがプロンプトの中の指示の山としてしか存在しないと、プロンプトを変える作業が危険になります。実装と仕様を同時に変えてしまうからです。振る舞いをシナリオとして別に置いておけば、プロンプトでもルーティングでもツールの説明でもモデルでも変えたあとに、「振る舞いは保たれたか」と同じ問いを立てられます。

ダッシュボードにパネルを追加させるタスクを例に、シナリオとエージェントとグレーダーの中身を並べてみましょう。以下は説明のために作った例で、公開されているベンチマークの実際の形式は後半の節で見ます。シナリオに書くのは、ユーザーの依頼と成功の条件です。

```yaml
request: |
  user-access-overview ダッシュボードに、キャッシュ更新の遅延のピークを示すパネルを追加してください。
  既存のパネルはそのまま残してください。
success:
  - 「Peak Cache Refresh Lag」というタイトルのパネルが保存されている
  - そのパネルのクエリが service_cache_refresh_lag_seconds を参照している
  - 追加する前からあったパネルが残っている
```

エージェントの側には、システムプロンプトと使えるツールの定義があります。

```text
あなたはGrafanaの操作を手伝うアシスタントです。
使えるツールは、ダッシュボードの取得、ダッシュボードの保存、Prometheusへのクエリです。
ダッシュボードを変更するときは、現在の内容を取得してから保存してください。
```

グレーダーは、エージェントの実行前と実行後にGrafanaのAPIから取得したダッシュボードを比べるスクリプトです。

```python
def grade(before, after):
    panels = {p["title"]: p for p in after["panels"]}
    added = panels.get("Peak Cache Refresh Lag")
    return {
        "パネルが追加された": added is not None,
        "クエリが対象のメトリクスを参照している": added is not None
            and any("service_cache_refresh_lag_seconds" in t.get("expr", "") for t in added["targets"]),
        "既存のパネルが残っている": all(p["title"] in panels for p in before["panels"]),
    }
```

シナリオにもグレーダーにも、プロンプトの文面は出てきません。グレーダーが見るのは保存されたダッシュボードだけなので、プロンプトを書き換えてもモデルを替えても、同じスクリプトでそのまま判定できます。

![シナリオとグレーダーを実装から分離する](/images/20261001-scenario-grader.png)

*図1: 実線は参照と判定の流れ、破線はタスクの受け渡しを表す。シナリオとグレーダーを仕様として別に置くと、右側の実装をどれだけ入れ替えても同じ問いを立てられる。*

良いシナリオの条件も4つ挙げられています。

- ベンチマークのために作られた不自然な問題ではなく、現実のユーザーの仕事に似ていること
- その領域に詳しい2人が、合否で一致する程度に具体的であること
- 言い回しの引っかけや指示の膨らみではなく、正しい理由で難しいこと
- 失敗したときに何かを教えてくれる程度に、扱う範囲が絞られていること

## 決定的な採点とルーブリック

グレーダーにも、シナリオと同じくらいの設計が必要です。記事のチームは、採点の対象によって方法を分けています。一方は決定的なチェックで、もう一方は**ルーブリック**[^rubric]を与えて**LLM-as-a-judge**[^judge]で判定させる方法です。

[^rubric]: 採点の基準を項目ごとに具体的に書き出した表のこと。教育分野で答案の評価に使われてきた用語で、「よく書けているか」のような全体的な印象ではなく、「正しいサービスを特定したか」「具体的な結果を提示したか」のように個別の観点へ分解して判定する。LLMに採点させる場合、この分解がないと判定がぶれる。

[^judge]: 出力の良し悪しをLLM自身に判定させる手法。人間が全件を読む方式に比べて速く安く回せるため、正解を一意に決められないタスクの評価で広く使われる。ただし判定するLLMにも偏りや不安定さがあるため、次節のように基準を明示したり、決定的なチェックと役割を分けたりする工夫が必要になる。

| 対象 | 方法 | 問いの例 |
|---|---|---|
| 構造化された出力 | 決定的な採点 | 正しいツールを呼んだか。正しい引数を渡したか。期待するクエリの形やパネルのスキーマを作ったか |
| より高次の基準 | ルーブリック付きの LLM-as-a-judge | 正しいサービスを特定したか。具体的な結果を提示したか。説明をタスクの出力に基づかせたか |

決定的なチェックは速く、再現でき、デバッグしやすいという利点があります。失敗したとき、たいてい理由がそのまま分かります。

![事実の検査と結論の検査](/images/20261001-grading-split.png)

*図2: 矢印は判定の流れを表す。同じ実行結果を2つの方法で検査し、結果を品質とコストとレイテンシの組で記録する。*

一方、LLMに判定させる部分では「これは良かったか」とは聞かず、明示的なルーブリックを与えて個別の基準ごとに答えさせます。記事では、曖昧な採点はほとんどの場合ノイズになる、としています。判定の基準を分解しないまま「良い回答か」と聞くと、同じ出力に対する判定が実行ごとに揺れ、改善の判断材料にならなくなるからです。

たとえば「checkoutのエラー率が上がった原因を調べてほしい」という依頼なら、ルーブリックは次のような形になります。これも説明のために作った例です。

| 基準 | 合格とする応答 | 不合格とする応答 |
|---|---|---|
| 原因のサービスを特定したか | エラーが増えたサービスを名前で挙げている | 「バックエンドのどこかで問題が起きている」とだけ述べている |
| 具体的な結果を提示したか | クエリで取得したエラー率の値と、上がった時間帯を示している | 「エラーが増えています」とだけ述べている |
| 説明をタスクの出力に基づかせたか | 挙げた根拠がすべてツールの実行結果に含まれている | 取得していないログやデプロイ履歴を根拠に挙げている |

判定するLLMには、エージェントの最終応答とツールの実行結果、そしてこの表を渡し、基準ごとに合否を答えさせます。「良い回答か」と1回で聞く場合と違い、どの基準で落ちたのかが結果から分かります。

2つの方法の境目は、合否が機械的に決まるかどうかです。決定的なチェックの対象は、正しいツールと引数、クエリの形、パネルのスキーマ、保存されたGrafanaの状態です。どれも期待する値と比べれば合否が決まるので、何度採点しても同じ判定になるチェックにできます。LLMに判定させるのは、原因のサービスの特定、具体的な結果の提示、説明がツールの実行結果に基づいているかどうかです。これらは応答の意味を解釈しないと合否が決まらないため、ルーブリックで基準を分けて判定させます。

グレーダーが見るものは、可能なかぎりユーザーが実際に体験する結果に寄せられています。具体的には、保存されたGrafanaの状態、クエリの構造、パネルのスキーマ、ナビゲーションの目的地、環境から取れる事実です。記事では、正確な言い回しは最適化する対象としてはたいてい最も面白くない部分だ、と述べられています。グレーダーを判定の基準となる状態や実際に取得した証拠に結び付けられるほど、判定は信頼でき、合否の差もはっきりします。

## 複数回走らせる理由

シナリオは複数回実行します。同じ種類のタスクがときどきしか成功しないなら、そのエージェントは信頼できるのではなく、たまたま成功しているだけだ、と記事は書いています。成功が実力なのか偶然なのかは、1回の実行では区別できないからです。

そして実行ごとに品質とコストとレイテンシを同時に記録します。品質を上げてコストを倍にする変更も、コストを下げながら重要なワークフローを合計スコアに現れないまま弱める変更も、それだけで採用に値するとは言えません。追いたいのは1つの数値ではなく、トレードオフが見える状態です。

比較は単独の数値ではなく、基準となる実行との差で行います。記事では、文脈のない78%という合格率には意味がなく、既知のベースラインに対する3ポイントの低下は大きな意味を持つ、としています。

## プロンプト改修の評価結果

Ekinciの記事では、この仕組みでプロンプトの改修を評価した結果も報告されています。社内の評価基盤で175のシナリオを各3回ずつ実行したものです。対象となった改修は、スポットチェックでは明確な改善に見えました。プロンプトのサイズが減り、構造が整理され、トークンの消費量も下がっています。

結果は能力の区分ごとに分けて示されています。区分はGrafana Assistantが担うタスクの種類で、それぞれ次のような仕事にあたります。

| 能力の区分 | 何をするタスクか | 改修前 | 改修後 |
|---|---|---|---|
| discover | 手元にどんなデータやサービスがあるかを探し当てる | 92.3% | 94.9% |
| safety | 破壊的な操作を確認なしに実行しないなど、安全側に振る舞う | 88.9% | 93.1% |
| observe | メトリクスやログを問い合わせて状態を読む | 93.6% | 79.5% |
| learn | 調べた内容をユーザーに説明する | 94.1% | 84.3% |
| dashboard | ダッシュボードやパネルを作る、直す | 100% | 83.3% |

区分名の定義は原文に明示されていないため、この対応はGrafana Assistantの機能から推定した説明です。合格率の数値は原文のとおりです。

トークンの消費量とコストは、原文では改修の利点として文章で述べられているだけで、区分ごとの内訳は公開されていません。上の表に載せたのは合格率だけです。この改修は、コストの面では歓迎すべきもので、品質の面では区分によって上下が分かれました。

品質の側を見ると、ダッシュボードが100%から83.3%へ落ちています。プロンプトを小さくして構造を整えた変更の結果です。

記事は、この結果について次のように述べています。

> If we had looked only at pass rate, we would have rejected the change. If we had looked only at cost, we probably would have shipped it immediately.
>
> （合格率だけを見ていたら、この変更を却下していただろう。コストだけを見ていたら、おそらく即座にリリースしていただろう）

記事は続けて、目的は1つのイエスかノーを見つけることではなく、トレードオフを見えるようにすることだった、と述べています。能力の区分ごとに割ったこの表があれば、「この改修は良かったのか」という曖昧な議論が、明示的な選択の問題になります。discoverとsafetyの改善は残し、observeとlearnの退行は区別し、ダッシュボードの低下は別の調査として扱う、という形です。全シナリオをまとめた合格率だけを見ていたら、この判断はできません。

## グレーダーの劣化

シナリオとグレーダーが揃うと、改善の手順を繰り返せるようになります。スイートを実行し、成功と失敗を検査し、変更を加え、同じ条件で再実行して比較します。手順そのものは単純です。

記事では、難しいのはこの過程を実際のエンジニアリングの判断に使える程度に信頼できるものにすることだ、と述べられています。ここがベンチマークと改善のループの分かれ目です。ベンチマークは、システムがタスクの集合に合格したか失敗したかを教えてくれるだけですが、ループはそれ以上を求められます。結果を採点するだけでなく、何が変わったのか、次に何をすべきかの理解を助け、繰り返し現れるパターン、弱いグレーダー、再発する失敗の形、そして改善に実際に支払った費用を明らかにする必要があります。

システムが十分に大きくなると、手作業での繰り返しは続かなくなりました。1回の実行で出てくる記録の量が、人間が読んで判断できる量を超えるからです。**トランスクリプト**[^transcript]、トレース、グレーダーの出力、区分ごとの差分、コストの変動、繰り返される失敗、不安定なシナリオ、脆いグレーダーが並びます。すべてを読んで人間が推論しきる方法は、この量では成り立ちません。

[^transcript]: エージェントが1つのタスクを処理する間のやり取りを、時系列にすべて記録したもの。ユーザーの要求、モデルが出力した思考や文章、呼び出したツールとその引数、ツールが返した結果が順番に並ぶ。最終的な応答だけを見ても分からない「途中でどう判断したか」は、ここにしか残らない。

そこで記事のチームは、ループを Evaluate、Learn、Changeの3段に分けて、Learnの段にAIコーディングエージェントを入れました。

![Evaluate、Learn、Changeの3段と人間の決定](/images/20261001-eval-loop.png)

*図3: 矢印はループの進行を表す。Evaluateはベンチマークの実行、Learnはコーディングエージェントによる証拠の分析、Changeは更新案にまとめる段で、採用するかどうかの判断は枠の外に置かれる。人間が採用を決めたら、その変更を入れた状態で左のEvaluateに戻る。*

Evaluateはベンチマークの実行そのもので、トランスクリプト、ツールの呼び出し履歴、グレーダーの出力、コスト、レイテンシ、能力ごとの結果を集めます。これが生の証拠です。

Learnでは、コーディングエージェントが失敗した実行と成功した実行を分析し、繰り返し現れるパターンを探し、弱いグレーダーと脆いアサーションを特定し、システムが実際に変化した区分を明らかにします。

Changeでは、その発見を具体的な更新に変えます。グレーダー側のキャリブレーションのこともあります。ルーブリックの基準を厳しくする、弱い基準を置き換える、誤った理由で合否が出ているシナリオを直す、といった作業です。エージェント側の改善のこともあります。指示を更新する、ツールの定義を変える、ルーティングを調整する、バグを直す、といった作業です。多くの場合は両方になります。

記事では、この役割分担を次の一文で表しています。

> It is a practical loop where AI proposes, benchmarks verify, and humans decide.
>
> （AIが提案し、ベンチマークが検証し、人間が決める、という実務的なループである）

記事では、自律的なプロダクト開発ではなく、モデルが裏で自分自身を書き換えるのでもない、と明示的に否定されています。人間が採用すると決めた変更を入れて、またEvaluateから測り直します。ここまでがループの1回分です。

ただし、このループは一度信頼できるようになればそのまま使い続けられるものではありません。記事では、シナリオは古びる、グレーダーはずれる、バリデータは脆くなりすぎる、環境についての前提は成り立たなくなる、と4つの劣化が並べられています。どれも放っておけば進むもので、グレーダーを見直し続けなければ、ループの結果は気付かれないうちに信用できないものになっている、ということです。だから記事は、グレーダーの改善を片手間の作業として扱わず、プロダクトの仕事の一部である、と書いています。

記事では、シナリオとグレーダーはYAMLを読むだけでは保守できない、とも指摘されています。タスクが不安定なとき、簡単すぎるとき、誤って採点されているとき、仕様が足りないとき、問題に決着をつけられるのは実際の実行から得た証拠だけです。トランスクリプト、採点の詳細、繰り返した実行、そしてそのタスクが検証しようとしている実際のシステムの状態がそれにあたります。

タスクが健全かどうかの基準も、書かれた文面の良さではなく、現実の仕事を反映しているか、試行をまたいで安定しているか、正しい理由で正しい振る舞いと誤った振る舞いを見分けられているかです。手直しの方法は場合によって異なり、バリデータの条件を厳しくすることも、ルーブリックを変えることも、共通のハーネスの挙動を直すこともあります。そのタスクが飽和している、あるいは設計が悪いと認めて差し替える場合もあります。

スイートを果てしなく大きくすることが目的ではない、とも述べられています。目指すのは、小さく、現実的で、1件ごとに得られる情報が多い状態を保つことです。記事では、現実のオブザーバビリティの仕事を反映して良いグレーダーを持つ小さなベンチマークは、曖昧で冗長で攻略しやすいタスクだらけの大きなベンチマークよりはるかに有用だ、と比較されています。

## シナリオの実物を読む

ここまでの話は社内の評価基盤についてのものですが、同じ設計を公開されたコードで確認できます。Grafana Labsは [o11y-bench](https://github.com/grafana/o11y-bench) というオブザーバビリティタスクのベンチマークをオープンソースで公開しており、シナリオの定義形式と採点の実装がそのまま読めます。

リポジトリの `tasks-spec/` がシナリオの正となる定義で、2026年9月時点で63個のYAMLが置かれています。カテゴリは6つあり、それぞれ次の内容です。

- **prometheus_query**（16個）：[Prometheus](https://prometheus.io/)のメトリクスを問い合わせて状態を答える。監視対象が今上がっているか、エラー率の急増が収まったか、キャッシュ更新の遅延がピーク時と現在でどう違うかなど
- **tempo_query**（13個）：[Tempo](https://grafana.com/oss/tempo/)のトレースから遅い経路や失敗を見つける。決済やチェックアウトで異常に遅い経路はどこか、トレースが取れているサービスはどれか、エラーを含むトレースがあるかなど
- **investigation**（11個）：複数のデータを突き合わせて因果を判断する。あるインシデントが広範なロールアウト起因なのか単一サービスに留まるのか、デプロイが警告の引き金と言えるだけの根拠が揃っているかなど
- **loki_query**（10個）：[Loki](https://grafana.com/oss/loki/)のログを検索して集計する。直近6時間で極端に遅いリクエストはどれか、どのサービスがデプロイを記録したか、再試行と本物のエラーをどう区別するかなど
- **dashboarding**（7個）：保存済みのダッシュボードを作る、直す。既存のパネルを保ったまま指定されたタイトルのパネルを追加する、デプロイを示す注釈を追加するなど
- **grafana_api**（6個）：Grafana自体の設定を調べる。ダッシュボードがどのデータソースを参照しているかパネルごとに突き合わせる、Prometheusデータソースの接続設定を答えるなど

READMEには「`tasks-spec/` is the source of truth for benchmark scenarios」とあり、生成物である `tasks/` を手で編集してはならないと明記されています。

1つ読んでみましょう。キャッシュ更新の遅延をPrometheusに問い合わせるタスクです。

```yaml
id: promql-cache-refresh-lag-peak
category: prometheus_query
statement: |
  We had an earlier user-service cache-refresh issue and I want the metric summary, not a general RCA.
  From Prometheus, tell me how high the user-service cache refresh lag got over roughly the last 12
  hours, what the lag is now at the end of the window, and whether that means the incident is still
  active or has recovered.
checks: []
rubric:
- criterion: The final response states Peak cache refresh lag accurately.
  weight: 45
  fact:
    kind: query
    backend: prometheus
    query: max_over_time(service_cache_refresh_lag_seconds{job="user-service"}[12h])
- criterion: The final response states Current cache refresh lag accurately.
  weight: 35
  fact:
    kind: query
    backend: prometheus
    query: service_cache_refresh_lag_seconds{job="user-service"}
```

この構造が、記事で読んだ設計とそのまま対応しています。

`statement` はユーザーの声で書かれた依頼です。採点の詳細はここに入れないという規則が grading/README.mdに明記されています（Keep `statement` user-voiced. Put grading detail in `checks`, `rubric`, and `fact`, not in the prompt）。エージェントに渡すのは依頼だけで、何を見て採点するかは伝えません。

`rubric` が判定の基準で、1項目ずつ独立した文になっています。「良い回答か」ではなく「ピーク値を正確に述べているか」と聞く形です。

そして `fact` には、基準ごとに正解を求めるためのクエリが書かれていて、採点時にそれを実行した結果が「Source of truth」として判定に渡されます。正解を文字列で固定しないため、エージェントが「約42秒」と書いても「42.3s」と書いても、同じ事実を指していれば合格です。記事にあった「グレーダーを、判定の基準となる状態や実際に取得した証拠に結び付ける」は、この `fact` として実装されています。

一方、保存された状態を問うタスクでは決定的なチェックが主な判定手段になります。ダッシュボードを編集させるタスクでは、`checks` に期待するパネルの構成が書かれ、さらに各パネルが保存しているクエリまで検証されます。

```yaml
checks:
- weight: 35
  type: state
  params:
    uid: user-access-overview
    mode: dashboard_state
    panels:
    - title: Peak Cache Refresh Lag
      type: stat
      datasource_type: prometheus
      execute_cases:
      - result_kind: prometheus_scalar
        canonical_query: max_over_time(service_cache_refresh_lag_seconds{job="user-service"}[$__range])
```

63タスク全体で、決定的な `checks` は39個、ルーブリックの基準は247個あり、そのうち63個に `fact` が付いています。この配分はカテゴリによってはっきり分かれます。dashboardingでは決定的なチェックの重みがタスクあたり平均91あり、タスクごとに全体の重みで正規化した平均では約88%です。prometheus_queryとloki_queryでは0です。保存された成果物は厳密に照合し、調査の結論はルーブリックで判定するという役割分担が、重み付けとして実装されています。記事にあった「事実には構造的なチェックを、結論には意味的なチェックを」という使い分けは、この配分に対応します。

採点の合成も単純です。`grading/verifier.py` が決定的なチェックを先に走らせ、次にルーブリックをまとめてLLMに渡し、両方の重みを合計1に正規化して加重平均を取ります。ルーブリックの判定を複数回に分けず1回の呼び出しにまとめるのは、設計方針として書かれています（Prefer a single judge call over multiple rubric passes）。

このベンチマークはPrometheusとLokiとTempoを含むGrafanaスタックを [Docker](https://www.docker.com/) で立てた中でエージェントを走らせ、デフォルトでは1タスクを3回試行します。前の節で見た「1回の実行では足りない」という点が、デフォルトの挙動です。採点だけを変えたときは、保存したトランスクリプトを使い回して再採点する仕組みもあります。エージェントを走らせ直さずにグレーダーのキャリブレーションを繰り返せるので、記事が「グレーダーの改善をプロダクトの仕事の一部として扱う」と書いていたことは、この仕組みにも反映されています。

なおo11y-benchはハーネスに依存しない設計です。エージェントの実装は差し替え可能で、MCP経由でGrafanaを操作するデフォルトのエージェントのほか、`gcx` CLI しか使えないエージェントも選べます。採点が単一の解法や言い回しを強制しない設計なので、この差し替えが可能です。ただし途中の手順を一切見ないわけではありません。たとえばTempoのタスクには、回答が挙げたトレースIDがツールの実行結果に実際に現れたかを確かめるチェックがあり、トランスクリプトを走査して確認しています。

## ベンチマークの外側

未解決の課題として、環境の忠実度が挙げられています。Grafana Assistantが動くのは、ダッシュボードとデータソースとプラグインとアラートルールと権限のある現実のGrafana環境の中です。有用なテストには現実的な統合と現実的なデータが必要ですが、同時に、比較が意味を持つ程度の安定性も必要になります。

> Too much simulation and you miss real failures. Too much live variability and the benchmark gets noisy.
>
> （シミュレーションが多すぎれば実際の失敗を見落とす。実環境の変動が多すぎればベンチマークがノイズだらけになる）

もう1つ、よく保守されたベンチマークのスイートであっても、制御されたタスクしか反映しないという限界があります。実際のユーザーは、想定していなかったことを、モデル化していなかった文脈で、シナリオに書き切れていなかった期待とともに尋ねてきます。

その隙間を埋めるために、記事のチームは本番の会話を採点して分析する仕組みを作りました。原文では、それが [Grafana Cloud](https://grafana.com/products/cloud/)のAI Observabilityにつながった、と述べられています。オフラインの評価ループに対応するオンライン評価の側という位置づけです。

この機能はその後 [Agent Observability](https://grafana.com/docs/grafana-cloud/observe-and-act/agent-observability/) に改名されています。[改名の告知](https://grafana.com/whats-new/2026-07-22-ai-observability-is-now-agent-observability--updated-branding-and-migration-guide/)では、ツール使用から評価、ガードレールまでエージェントのライフサイクル全体を対象にするようになったため名前を追いつかせた、と説明されています。

本番の会話を見ることで、ベンチマークだけでは得られない情報が手に入ります。ユーザーが実際に不満を感じている箇所と、実務で問題になる失敗がどれかという視点です。記事では、ベンチマークの結果と本番の評価を比べる読み方も挙げられています。アラートに関するシナリオはスイートでは通るのに、アラートに関する会話が本番では低く評価されるなら、スイートが何か重要なものを取りこぼしているということです。逆に、ベンチマークで見えた退行が本番の品質データに現れないなら、ユーザーがそこまで価値を置いていない何かを、自分たちが重く見すぎている可能性があります。

現時点では、本番から得た洞察はシナリオを追加したり改良したりする判断に使われています。将来はその段も自動化されたループの一部にしたい、と書かれています。実際の会話から出た失敗が自動的にシナリオの候補になり、コーディングエージェントがスイートへの追加を提案し、人間が採用するものを審査する形です。

ペースの問題も消えないと報告されています。プロダクトの開発が評価の網羅より速く進むからです。記事では、新しいツールとワークフローは、それをシナリオにするより速く追加されることが多い、と述べられています。評価がリリースを止めることは望まないが、システムが最も速く変化しているところに盲点があるのも望ましくない、という立場です。そこで影響の大きいワークフローから先に評価を整え、シナリオが足りていない領域のうちどれを急ぐべきかは、本番の品質データを見て判断するという進め方をとっています。

現実的なデータと安定した比較のどちらを取るかという選択は、実際に評価の結果を左右します。同じチームの William Dumont は[別の記事](https://medium.com/grafana-labs/enter-the-arena-evaluating-and-improving-grafana-assistant-investigations-against-real-incidents-d0a813404ad2)で、合成テレメトリーで作った環境では評価が合格し続けたのに、実インシデントでは重要な部分で苦戦していた、と報告しています。

## 自分でループを始める

記事は最後に、自分のところで同じループを始めるための最小限の手順を挙げています。ツールそのものは社内のものですが、方法は移植できる、という位置づけです。

まず小さく始めます。数百のシナリオは必要なく、よくあるワークフローと実際の失敗から取った現実的なタスクが数十あれば始められます。

シナリオには成功条件を明示します。その領域に詳しい2人が合否で一致しないなら、そのシナリオはおそらく仕様が足りていません。定義する内容は、文脈と、使えるツールと、望む結果です。1つの正確な言い回しに過剰適合させないようにも書かれています。

グレーダーは結果を先に評価します。特定の経路を通ることが方針として要求されるのでなければ、エージェントが別の妥当な方法で正しい結果に到達したことを理由に失敗とはしません。エージェントは自分では設計しなかったやり方を見つけることがあるためです。言い回しを主に検査するグレーダーより、実際に取得した状態や保存された成果物やクエリの構造といった、基準として使える証拠を見るグレーダーを選びます。

品質とコストとレイテンシは一緒に追います。効率が改善したときは、タスクの完遂に何を支払ったか確かめてから評価します。

要約のスコアではなくトランスクリプトを読みます。グレーダーのバグや曖昧なシナリオや環境の問題が隠れているのはそこだからです。証拠を読むまで、自分のグレーダーが機能しているかどうかは分かりません。

そして評価の基盤をプロダクトとして扱います。テストしている対象のエージェントと同じように、保守とデバッグと投資が必要です。前の節で見た4つの劣化は放っておけば進むので、最初からその分を見込んでおきます。

オブザーバビリティに馴染んだ読者には、この姿勢はそのまま通じるはずです。計装して、検査して、改善します。違うのは、観測している対象がインフラではなくエージェントの振る舞いだという点だけです。

## おわりに

この記事で扱った評価ループは、Grafana Assistantに固有の機能ではありません。望ましい振る舞いをシナリオとして実装から切り離し、判定の結果から次の変更を決めるという、AIエージェントの品質を継続的に確かめるための考え方です。o11y-benchでも、この考え方が公開されたシナリオと採点の形式として成り立っていることを確認できました。

最初から大規模な評価基盤を作る必要はありません。よくあるワークフローから少数のシナリオを作り、成功条件を明示するところから始めてください。実行結果は合計のスコアだけで判断せず、トランスクリプトまで読んで確かめます。シナリオは古び、グレーダーはずれていくので、評価基盤も保守の対象として扱ってください。具体的な書き方に迷ったら、o11y-benchの `tasks-spec/` にあるシナリオ定義が参照先になります。

対象が別のエージェントや別の業務であっても、この評価ループは同じ形で応用できます。もっともらしく見える失敗は、最終応答だけでは見分けられません。どのツールを呼び、何を根拠に結論を出したかという実行の過程まで評価してください。そして評価の結果を、エージェントとグレーダーの両方の改善につなげてください。
