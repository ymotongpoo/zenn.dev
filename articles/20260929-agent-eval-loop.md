## この記事で扱うこと

AIエージェントに可観測性の仕事をさせたとき、その答えが良くなったのか悪くなったのかを、どうやって知るのでしょうか。

Grafana Cloud には [Grafana Assistant](https://grafana.com/docs/grafana-cloud/machine-learning/assistant/) というエージェントが組み込まれています。メトリクスを問い合わせ、ログとトレースを探索し、ダッシュボードを作り、自然言語で Grafana を操作します。それを開発しているチームは、評価の仕組みを作った経緯と、そこで見つけたことを公式のエンジニアリングブログで公開しています。この記事では [Building an evaluation loop for Grafana Assistant](https://medium.com/grafana-labs/building-an-evaluation-loop-for-grafana-assistant-9a8690d8662d)（Yasir Ekinci、2026年4月30日）の内容を追いながら、エージェントの評価をどう組み立てるかを見ていきます。

続編では、同じ Grafana Labs が公開したインシデント調査の評価事例を取り上げ、測定からどのような改善が見つかったかを追います。

## もっともらしく見える失敗

記事の冒頭に、評価が難しい理由が書かれています。

> the hardest failures usually aren’t the obvious ones; they’re the ones that look plausible on the surface.
>
> （最も難しい失敗はたいてい明白なものではなく、表面上もっともらしく見えるものである）

具体例も2つ挙げられています。答えは良く書けているのに、間違ったクエリに基づいている。パネルは正常に描画されるのに、ユーザーが何かを理解する助けにはなっていない。どちらも、最終的な応答を読むだけでは見落とすことがあります。

エージェントがタスクに従っているように見えながら、途中のどこかで悪い判断を下していることもあります。しかもシステムは非決定的なので、同じ要求が一度は成功しても、次には失敗することがあります。可観測性のタスクは答えの形が定まっておらず、複数の手順を踏むことが多いため、この種の静かな失敗はとくに見落としやすくなります。

そこで評価の対象が変わります。

> For a tool-using agent, the final answer is only part of the behavior. The rest is hidden in the steps that produced it.
>
> （ツールを使うエージェントにとって、最終的な答えは振る舞いの一部にすぎない。残りは、それを生み出した手順の中に隠れている）

どのツールを呼んだか、どんな引数を渡したか、結果をどう解釈したか、次に何をしたか、そして結果をどうユーザーに伝えたか。見るべきものはこの軌跡の全体です。出力だけを検査する方法では足りません。

## シナリオを仕様として置く

軌跡を見るために、記事のチームはプロンプトを唯一の基準として扱うのをやめました。代わりに書いたのがシナリオとグレーダーです。

**シナリオ**は現実のユーザーのワークフローと、成功が何を意味するかを記述します。**グレーダー**は、その成功が実際に起きたかを判定します。判定の根拠に使うのは、ツールの引数、クエリの構造、保存された Grafana の状態、ナビゲーションの目的地、環境から実際に取得できる事実です。シナリオが望ましい振る舞いを定義し、グレーダーがそれを達成できたかを教えます。

この分離が意味を持つ理由は、原文の一文に凝縮されています。

> The desired behavior is encoded separately from how the implementation achieves it, whether that implementation is the agent itself, its prompt, its routing logic, or the code around it.
>
> （望ましい振る舞いは、実装がそれをどう達成するかとは別に符号化される。その実装がエージェント自身であれ、プロンプトであれ、ルーティングのロジックであれ、周辺のコードであれ変わらない）

望ましい振る舞いがプロンプトの中の指示の山としてしか存在しないと、プロンプトを変える作業が危険になります。実装と仕様を同時に変えてしまうからです。振る舞いをシナリオとして別に置いておけば、プロンプトでもルーティングでもツールの説明でもモデルでも変えたあとに、同じ問いを立てられます。振る舞いは保たれたか、と。

![シナリオとグレーダーを実装から分離する](/images/20260929-scenario-grader.png)

*図1: 実線は参照と判定の流れ、破線はタスクの受け渡しを表す。シナリオとグレーダーを仕様として別に置くと、右側の実装をどれだけ入れ替えても同じ問いを立てられる。*

良いシナリオの条件も書かれています。ベンチマーク特有の謎かけではなく、現実のユーザーの仕事に似ていること。その領域に詳しい2人が合否で一致する程度に具体的であること。正しい理由で難しいこと。言い回しが引っかけになっているのでも、指示が膨らんでいるのでもなく。そして失敗したときに何かを教えてくれる程度に、扱う範囲が絞られていること。

## 決定的な採点とルーブリック

グレーダーはシナリオと同じくらい設計が要ります。記事のチームは、採点の対象によって方法を分けています。

| 対象 | 方法 | 問いの例 |
|---|---|---|
| 構造化された出力 | 決定的な採点 | 正しいツールを呼んだか。正しい引数を渡したか。期待するクエリの形やパネルのスキーマを作ったか |
| より高次の基準 | ルーブリック付きの LLM-as-judge | 正しいサービスを特定したか。具体的な結果を提示したか。説明をタスクの出力に基づかせたか |

決定的なチェックは速く、再現でき、デバッグしやすい。失敗したとき、たいてい理由がそのまま分かります。

![事実の検査と結論の検査](/images/20260929-grading-split.png)

*図2: 矢印は判定の流れを表す。同じ軌跡を2つの方法で検査し、結果を品質とコストとレイテンシの組で記録する。*

一方、LLM に判定させる部分では「これは良かったか」と聞きません。明示的なルーブリックを与えて、個別の基準ごとに答えさせます。理由は簡潔に書かれています。

> Vague grading is almost always noise.
>
> （曖昧な採点は、ほとんどの場合ノイズである）

この使い分けは、記事の中で教訓として一文にまとめられています。事実には構造的なチェックを、結論には意味的なチェックを。

可能なかぎり、ユーザーが実際に体験する結果を評価しようとしている点も見ておきたいところです。保存された Grafana の状態、クエリの構造、パネルのスキーマ、ナビゲーションの目的地、環境から取れる事実。正確な言い回しは、最適化する対象としてはたいてい最も面白くない部分だと書かれています。グレーダーを、判定の基準となる状態や実際に取得した証拠に結び付けられるほど、判定は信頼できて弁別力を持つようになります。

## 複数回走らせる理由

シナリオは複数回実行します。

> One run is not enough. If a capability only passes occasionally, that is not reliable — it’s luck.
>
> （1回の実行では足りない。ある能力がときどきしか通らないなら、それは信頼できるのではなく、運である）

そして実行ごとに品質とコストとレイテンシを同時に記録します。品質を上げてコストを倍にする変更は、自動的に勝ちではありません。コストを下げながら重要なワークフローを静かに弱める変更も、出荷に値するとは限りません。追うべきは1つの数値ではなく、トレードオフが見える状態です。

比較の相手も指定されています。単独の数値ではなく、基準となる実行との差を見ます。文脈のない78%という合格率には意味がなく、既知のベースラインに対する3ポイントの低下にはすべての意味がある、というのが記事の言い方です。

## 175シナリオの実測結果

以上の仕組みが何を拾うのかを、記事は実例で示しています。Ekinci の記事では、社内の評価基盤で175のシナリオを各3回ずつ実行した結果が報告されています。対象となったプロンプトの改修は、スポットチェックでは明確な改善に見えました。プロンプトのサイズが減り、構造が良くなり、トークンの消費量も下がっています。

結果はこうなりました。

| 能力の区分 | 改修前 | 改修後 |
|---|---|---|
| discover | 92.3% | 94.9% |
| safety | 88.9% | 93.1% |
| observe | 93.6% | 79.5% |
| learn | 94.1% | 84.3% |
| dashboard | 100% | 83.3% |

ダッシュボードが100%から83.3%へ落ちています。プロンプトを小さくして構造を整えた変更の結果です。

記事はこの一件から結論を引き出しています。

> If we had looked only at pass rate, we would have rejected the change. If we had looked only at cost, we probably would have shipped it immediately.
>
> （合格率だけを見ていたら、この変更を却下していただろう。コストだけを見ていたら、おそらく即座に出荷していただろう）

目的は1つのイエスかノーを見つけることではなく、トレードオフを見えるようにすることだった、と続きます。能力の区分ごとに割ったこの表があれば、「この改修は良かったのか」という曖昧な議論が、明示的な選択の問題に変わります。discover と safety の改善は残し、observe と learn の退行は切り分け、ダッシュボードの低下は別の調査として扱う、というように。

合計スコアだけを見ていたら、この判断はできません。

## グレーダーの劣化

シナリオとグレーダーが揃うと、周回ができるようになります。スイートを実行し、成功と失敗を検査し、変更を加え、同じ条件で再実行して比較する。形は単純です。

難しいのは、この過程を実際のエンジニアリングの判断に使える程度に信頼できるものにすることだ、と記事は書いています。ここにベンチマークと改善のループの違いがあります。ベンチマークは、システムがタスクの集合に合格したか失敗したかを教えてくれます。ループはそれ以上を求められます。何が変わったのか、次に何をすべきかの理解を助けなければなりません。結果を採点するだけでなく、繰り返し現れるパターン、弱いグレーダー、再発する失敗の形、そして改善に実際に支払った費用を浮かび上がらせる必要があります。

手作業での反復が破綻したのはこの段でした。システムが十分に大きくなると、ベンチマークは人間が効率的に消化して行動に移せる量を超える証拠を生みます。トランスクリプト、トレース、グレーダーの出力、区分ごとの差分、コストの変動、繰り返される失敗、不安定なシナリオ、脆いグレーダー。すべて読んで手で推論し通す方法は、そこで規模に対して成り立たなくなります。

そこで記事のチームは、周回を Evaluate、Learn、Change の3段に分けて、Learn の段にAIコーディングエージェントを入れました。

Evaluate はベンチマークの実行そのもので、トランスクリプト、ツールの軌跡、グレーダーの出力、コスト、レイテンシ、能力ごとの結果を集めます。これが生の証拠です。

Learn では、コーディングエージェントが失敗した実行と成功した実行を分析し、繰り返し現れるパターンを探し、弱いグレーダーと脆いアサーションを特定し、システムが実際に変化した区分を浮かび上がらせます。

Change では、その発見を具体的な更新に変えます。ルーブリックを締める、弱い基準を置き換える、誤った理由で合否が出ているシナリオを直す、といったグレーダー側の較正のこともあります。指示を更新する、ツールの定義を変える、ルーティングを調整する、バグを直す、といったエージェント側の改善のこともあります。多くの場合は両方です。

この関係は一文で定式化されています。

> It is a practical loop where AI proposes, benchmarks verify, and humans decide.
>
> （AIが提案し、ベンチマークが検証し、人間が決める、という実務的なループである）

自律的なプロダクト開発ではなく、モデルが裏で自分自身を書き換えるのでもない、と明示的に否定されています。

ただし、このループは一度信頼できるようになったらそのままではありません。

> Scenarios go stale. Graders drift. Validators become too brittle. Environment assumptions stop holding.
>
> （シナリオは古びる。グレーダーはずれる。バリデータは脆くなりすぎる。環境についての前提は成り立たなくなる）

グレーダーを締め直し続けなければ、周回は静かに劣化します。だから記事は、グレーダーの改善を片手間の作業として扱いません。プロダクトの仕事の一部である、と書いています。

シナリオとグレーダーはYAMLだけでは保守できない、という指摘も具体的です。タスクが不安定なとき、簡単すぎるとき、誤って採点されているとき、仕様が足りないとき、問題を決着させられるのは生きた証拠だけになります。トランスクリプト、採点の詳細、繰り返した実行、そしてそのタスクが検証しようとしている実際のシステムの状態です。

タスクが健全かどうかの基準も、書かれていた文面の良さではありません。現実の仕事を反映しているか、試行をまたいで安定しているか、正しい理由で正しい振る舞いと誤った振る舞いを弁別できているか。ときにはバリデータを締め、ときにはルーブリックを変え、ときには共通のハーネスの挙動を直し、ときにはそのタスクが飽和している、あるいは設計が悪いと認めて差し替えることになります。スイートを果てしなく大きくすることが目的ではない、とも述べられています。目指すのは、小さく、現実的で、信号の濃い状態を保つこと。現実の可観測性の仕事を反映して良いグレーダーを持つ小さなベンチマークは、曖昧で冗長で攻略しやすいタスクだらけの大きなベンチマークよりはるかに有用だ、という比較が置かれています。

## ベンチマークの外側

未解決の難所として、環境の忠実度が挙げられています。Assistant は、ダッシュボードとデータソースとプラグインとアラートルールと権限のある現実の Grafana 環境の中で動きます。有用なテストには現実的な統合と現実的なデータが必要ですが、同時に、比較が意味を持つ程度の安定性も必要になります。

> Too much simulation and you miss real failures. Too much live variability and the benchmark gets noisy.
>
> （シミュレーションが多すぎれば実際の失敗を見落とす。実環境の変動が多すぎればベンチマークがノイズだらけになる）

もう1つ、よく保守されたベンチマークのスイートであっても、制御されたタスクしか反映しないという限界があります。実際のユーザーは、想定していなかったことを、モデル化していなかった文脈で、完全には符号化できていなかった期待とともに尋ねてきます。

その隙間を埋めるために、記事のチームは本番の会話を採点して分析する仕組みを作りました。それが Grafana Cloud の AI Observability につながっています。オフラインの評価ループに対する、オンライン評価の側の対応物だという位置づけです。

これはベンチマークだけでは得られないものを与えます。ユーザーが実際に不満を感じている箇所と、実務で問題になる失敗がどれかという視点です。記事に挙げられた読み方が具体的で参考になります。アラートに関するシナリオはスイートでは通るのに、アラートに関する会話が本番では低く評価されるなら、スイートが何か重要なものを取りこぼしていることを意味します。逆に、ベンチマークで見えた退行が本番の品質データに現れないなら、ユーザーがそこまで価値を置いていない何かを、自分たちが重く見すぎている可能性があります。

現時点では、本番から得た洞察はシナリオを追加したり改良したりする判断に使われています。将来はその段も自動化されたループの一部にしたい、と書かれています。実際の会話から出た失敗が自動的にシナリオの候補になり、コーディングエージェントがスイートへの追加を提案し、人間が採用するものを審査する形です。

ペースの問題も消えないと認められています。プロダクトの開発は評価の網羅より速く進みます。新しいツールとワークフローは、それをシナリオに落とし込めるより速く到着することが多い。評価が出荷を止めることは望まないが、システムが最も速く変化しているところに盲点があるのも望まない。だから影響の大きいワークフローから優先し、どの隙間がユーザーに最も痛みを与えているかは本番の信号に教えてもらう、という運び方になっています。

この緊張が実際にどう現れたかは、続編で扱います。インシデント調査の評価事例では、合成したデータで作った環境が通り続けながら、実インシデントでは重要な部分で苦戦していたと報告されています。評価の考え方は共通しますが、同じ評価基盤やデータセットだと公開資料から確認できるわけではありません。

## 自分でループを始める

記事は最後に、自分のところで同じ周回を始めるための最小の出発点を挙げています。ツールそのものは社内のものですが、方法は移植できる、という位置づけです。

小さく始めます。数百のシナリオは要りません。よくあるワークフローと実際の失敗から取った、現実的なタスクが数十あれば始められます。

シナリオには成功条件を明示します。その領域に詳しい2人が合否で一致しないなら、そのシナリオはおそらく仕様が足りていません。文脈と、使えるツールと、望む結果を定義します。1つの正確な言い回しに過剰適合させないようにも書かれています。

グレーダーは結果を先に評価します。特定の経路を通ることが方針として要求されるのでなければ、エージェントが別の妥当な方法で正しい結果に到達したことを理由に失敗としません。エージェントは、自分では設計しなかったやり方を見つけることがあります。言い回しを主に検査するグレーダーより、実際に取得した状態や保存された成果物やクエリの構造といった、基準として使える証拠を見るグレーダーを選びます。

品質とコストとレイテンシは一緒に追います。効率の勝ちを、タスクの完遂に何を支払ったか確かめずに祝わないこと。

要約のスコアではなくトランスクリプトを読みます。グレーダーのバグや曖昧なシナリオや環境の問題が隠れているのはそこだからです。証拠を読むまで、自分のグレーダーが機能しているかどうかは分かりません。

そして評価の基盤をプロダクトとして扱います。テストしている対象のエージェントと同じように、保守とデバッグと投資が必要になります。グレーダーはずれ、シナリオは古び、環境の変更は前提を壊します。最初からその分を見込んでおくこと。

可観測性に馴染んだ読者には、この姿勢はそのまま通じるはずです。計装して、検査して、改善する。違うのは、観測している対象がインフラではなくエージェントの振る舞いだという点だけです。
